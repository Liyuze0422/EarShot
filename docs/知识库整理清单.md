# 知识库整理清单

> 这份清单不是"建议"，每一条都对应检索代码里的一个具体机制。
> 不按它写，材料放进去也检索不出来。

## 为什么需要这份清单

同一份简历、同一个岗位，不同人整理出来的知识库，**回答命中率能差一倍以上**。
原因是 retrieval 是词级 BM25 + 文件名加权 + 话题加权，它对材料的**结构**极其敏感：

| 实测（39 条真实提问，hit@1） | |
|---|---|
| 基线 | **89.7%** |
| 掺入 25% 「讲同一批话题」的别人的经历 | **41.0%** ← 腰斩 |
| 掺入 2 倍**异题材**文档 | 87.2%（只掉 2.5） |

**结论：同题材的材料会直接抢排名。** 整理知识库最大的风险不是"材料太少"，
而是"把别人的、泛泛而同题材的东西混进来"。

---

## 一、放哪里

```
knowledge/
├── _base/            ← 所有面试通用的个人材料（你的项目、经历、技能）
└── <公司名>/          ← 某家公司/某一轮专用（JD、公司介绍、面经）
```

- 面试哪家就切哪个包（`tools/profiles.py --use <名>`）。
- **不要把别人的面经、培训机构的《XX面试宝典》放进 `_base/`** —— 它们讲的话题和你
  的材料高度重合，会把真正该命中的那份挤下去（就是上表 89.7%→41.0% 那个坑）。
- 公司专用的东西放公司包。切包时它才生效，不会污染别的面试。

## 二、文件怎么命名（这条最关键）

**文件名在检索词袋里会被重复 4 次**（`TITLE_WEIGHT = 4`），权重远高于正文里的任何词。
所以文件名不是给人看的标签，它是**检索键**。

命名格式：

```
<项目名>_<主题>_<类型>.md
```

| ✅ 好 | ❌ 差 | 为什么 |
|---|---|---|
| `项目3_LoRA微调_深度分析.md` | `面试材料3.md` | 后者完全不含主题词 |
| `项目1_推荐系统_双塔召回.md` | `我的项目.md` | 面试官说"推荐系统""双塔"时打不中 |
| `HR初面准备_离职原因.md` | `HR.md` | 太泛，会跟所有 HR 话题抢 |

**还要和 `config/topic_terms.json` 对齐**：那个文件把"面试官口语里的词"映射到
"文件名里的片段"。比如：

```json
{ "项目3": ["微调", "LoRA", "QLoRA", "量化", "显存", "训练集"] }
```

面试官说"你这个微调是怎么做的"→ 命中"微调"→ 文件名含"项目3"的材料加权 3 倍。
**如果文件名里没有"项目3"这个片段，这个加权就落空了。**

## 三、正文怎么写

### 3.1 按标题切块，每块 60~700 字

切块规则：`re.split(r'\n(?=#{1,4}\s)', text)` —— **按 `##`/`###`/`####` 标题切**。

- 每块 `< 60` 字会被**丢弃**（太短没信息）
- 每块 `> 700` 字会被**硬切**（可能从句子中间切断，语义破碎）
- 所以：**每个 `##` 小节控制在 60~700 字**。超了就再分一个 `##`

### 3.2 每块必须自带主语

检索是**按块**的。一块被单独取出来时，如果没有主语，模型不知道在说哪个项目。

❌
```markdown
## 技术选型
用了 Milvus，因为需要混合检索。
```

✅
```markdown
## 项目3_LoRA微调 · 技术选型
这个项目里向量库选了 Milvus，因为要做稠密+稀疏的混合检索，
Qdrant 的稀疏支持当时还不成熟。
```

### 3.3 每块的结构模板

一个能被追问的项目材料，建议每块都覆盖这七件事：

| 要素 | 面试官会怎么问 | 你要写什么 |
|---|---|---|
| 背景 | "这是个什么项目？" | 一句话说清做什么、给谁用 |
| 我的角色 | "你负责哪块？" | 明确边界，别写"我们" |
| 选型与理由 | "为什么用 X 不用 Y？" | **理由 + 备选 + 为什么淘汰** |
| 关键数字 | "效果怎么样？" | 带具体数字（延迟/准确率/规模） |
| 踩过的坑 | "遇到什么困难？" | 具体故障 + 怎么定位 + 怎么修 |
| 可追问点 | （面试官接着问的） | 提前写好第二三层答案 |
| 不会的 | （问到你不会的） | 准备好"这块我没深入"的体面说法 |

**"选型理由"和"关键数字"是最常被追问的两块，也是最多人写不全的两块。**

## 四、三份配置（决定检索能不能命中）

放在 `config/`（已 gitignore，不会进公开仓库）：

### 4.1 `config/domain_words.txt` — 钉住会被切碎的专业词

jieba 会把"工作流"切成"工作/流"、"有向图工作流"切成"有向图/工作/流"，
术语对不上就检索不到。**一行一个词**。

判断标准：**你项目里的产品名、技术栈缩写、内部黑话**。
拿不准就把词贴进去，多了不亏。

### 4.2 `config/topic_terms.json` — 话题词 → 材料归属

```json
{
  "项目1": ["无人机", "地面站", "航线"],
  "项目2": ["质检", "工控机", "页码"]
}
```

键 = **文件名里能区分项目的片段**（必须和文件名一致！）
值 = **面试官口语里会说的词**
命中 → 对应材料加权 3 倍（实测 hit@1 51.3%→69.2%）。

### 4.3 `config/known_terms.md` — 你会说的技术名词

**这份现在是双份收益**：
1. 判定"这题我是不是没准备过"
2. **ASR 术语纠错的目标词表** —— 新版会把转写里听错的英文词往这份表上纠
   （实测英文术语识别率 35.7% → 54.3%）

所以**把你项目里所有的技术名词都写进去**，中文英文都要。
没写进这份表的词，纠错帮不了你。

## 五、面试官不会照抄你的说法

**这是检索失败的最大单一来源，实测过。**

你材料里写「LangGraph 九节点有向图工作流」，面试官问的可能是
「你那套任务编排是怎么设计的」；你写「自然语言解析三级降级链」，
他问「你说的那套语义理解具体指什么」。**一个字都不重合。**

字面重合为零，词级 BM25 就无从下手。实测（19 条换说法基准，同一套材料）：

| 面试官的说法 | hit@1 | hit@3 |
|---|---|---|
| 照抄你的材料措辞 | 61.5% | 74.4% |
| **换成他自己的通用说法** | **15.8%** | **42.1%** |

### 怎么解决：离线把面试官的说法预先编进索引

```powershell
python tools/kb_expand.py --dry-run   # 先看还差多少块，不调模型
python tools/kb_expand.py             # 增量生成（可中断，下次续跑）
```

它逐块读你的材料，让模型生成 5 个「面试官可能怎么问这块」的通用问法，
编进这一块的检索词袋。**运行时不发任何请求**，延迟和花费都不变。

产物是 `config/doc_expand.json`，按**内容 hash** 索引：材料改一个字，
这块就自动没有扩展词、退回纯原文检索，不会张冠李戴。

它是**构建产物，由你的私有材料生成，不要提交**（`.gitignore` 已挡）。
**材料改了要重跑**，`--dry-run` 会告诉你还有多少块没覆盖。

### 你能配合的那一半

扩展词只能覆盖到"能想到的说法"。所以写材料时：
**重要的概念，原文里就顺手把它的常见别名写一次。**

例如「自然语言解析三级降级链（NLU 降级、意图解析兜底）」——
一句话的成本，比事后调试便宜得多。

## 六、反面清单（做了会让效果变差）

| ❌ 不要 | 后果 |
|---|---|
| 放别人的面经/面试宝典 | 同题材抢排名，hit@1 腰斩 |
| 放整本书、整个文档库 | 同上，而且块大小失控 |
| 一个 `##` 写 2000 字 | 被硬切，语义破碎 |
| 文件名用 `材料1.md` | 浪费 4 倍权重的文件名通道 |
| 通篇"我们团队" | 面试官问"你做了什么"时答不上 |
| 只写结论不写理由 | 一追问就崩 |
| 写没做过的技术 | 追问三层就露馅 |

## 七、自检：跑一遍审计

```powershell
python tools\kb_audit.py
```

它会报告：
- 有多少块会被丢弃（< 60 字）、有多少块会被硬切（> 700 字）
- 文件名里不含任何话题词的文件
- 块里没有项目归属的
- 疑似外部材料（同题材但用词风格和你其余材料差异大）

## 八、让 AI 帮你整理

```powershell
python tools\kb_prompt.py --resume 我的简历.md --jd 岗位JD.md
```

它会把你自己的实际情况 + 上面的规则拼成一段可直接发给 AI 的提示词，
让 AI 按这个规范产出材料。**产出后仍然要跑 `kb_audit.py` 自检**，
再自己读一遍 —— AI 编的项目细节是面试最大的坑。

## 九、部署味道优先：别让材料只喂出"道理"

> 这一节是**实测出来的**，不是建议。

### 9.1 现象：面试官问"你怎么做"，提词器答的是"一般我会……"

用一份只有技术方案、没有现场动作的材料跑四条典型问题，输出是这样的：

| 问题 | 答案里有什么 | 【数字】栏 |
|---|---|---|
| 你在客户现场部署过吗？ | "部署过，客户内网私有化部署我全程跟过" + 抽象展开 | **无** |
| 怎么评估一个项目的开发周期？ | 通篇方法论："先列风险点，再按风险倒推时间" | **无** |
| 你们系统最后怎么交付上线？ | 前半段通用做法（灰度 / 手册 / 响应机制） | **无** |
| 跟硬件对接遇到过什么问题？ | 有具体事件（非标字节），但没有环境、没有对手方 | **无** |

**四条里三条是通用道理，数字栏全是"无"。**

根因不在模型，在**材料**：知识库里只有"技术选型 / 技术点"这类材料，
**没有一份专门写"我在现场做了什么"的材料**。检索不到事实，模型只能拿通用知识把空位填满——
于是屏幕上出现的全是"我会先定边界""一般我会先搭骨架"这种**没做过事也能说的话**。

真实面试的后果：面试官追问一层就没了。而这类"你怎么看 / 你怎么评估"的问题，
恰恰是老板型面试官最爱问的（他不考技术细节，他考你是不是真的干过）。

### 9.2 硬要求：知识库里必须有一份"现场部署与交付"材料

在 `_base/` 下建一份，文件名要带检索键（面试官的口语词能对上）：

```
_base/现场部署与交付_软件侧实战.md
```

它至少要覆盖这七块，**每块都要有环境、对手方、我的动作、结果**：

| 块 | 写什么 | 面试官会怎么问 |
|---|---|---|
| 边界声明 | 我做的部署是哪一类、**不是什么**（诚实说没做过的） | "你部署过吗？" |
| 环境约束 | 客户内网 / 无外网 / 低配机器，因此改了什么设计 | "内网环境你们怎么装？" |
| 对接踩坑 | 对方不标准的地方 + 我的定位动作 + 结果 | "跟硬件对接遇到过什么问题？" |
| 链路验证 | "通"的标准是什么（心跳 / 实流 / 握手），不是"端口能连" | "你怎么确认链路是通的？" |
| 上线前验证 | 仿真 / 预发怎么跑，异常场景怎么注入 | "没真机你怎么验证？" |
| 交付收尾 | 灰度、通过线、手册、响应机制 | "怎么算交付完成？" |
| 工期怎么估 | 分段 + 最不确定的那一段 + 汇报节奏 | "这个你要做多久？" |

### 9.3 每一条经历必须凑齐这五个要素

| 要素 | 反例 | 正例 |
|---|---|---|
| **环境** | "客户那边部署过" | "客户内网、没有外网、只能本地跑模型" |
| **对手方** | "跟硬件一起解决的" | "厂商用的起始字节是非标准的 0xFC，拉硬件一起确认帧结构" |
| **我的具体动作** | "我做了定位" | "写最小复现、抓原始字节跟标准协议逐字节比对" |
| **约束 / 故障** | "遇到一些问题" | "按标准解析会误伤载荷数据" |
| **结果（带数字最好）** | "最后解决了" | "加了一层字节翻译代理，**不改宿主软件**就把链路接进去了" |

**判定标准（一句话）**：把这条块单独拿出来，**另一个人照着能不能复现你的动作**。
不能，那就是道理，不是经历。

### 9.4 反面清单：这些话出现在答案里，说明材料没写够

| ❌ 句子 | 为什么是信号 |
|---|---|
| "我会先定边界和成功标准" | 没做过的人也会说 |
| "一般我会先搭骨架，再往里面填内容" | 同上，且没有任何项目锚点 |
| "要分情况看 / 具体要看场景" | 把选择权推回给面试官 |
| "我理解最重要的是……" | 判断没有事实垫底 |
| "我做过不少风险预测" | 有动词没有事件 |

**材料里只要有足够的"环境 + 对手方 + 动作"，这些句子自然会被挤出去**——
模型的空位被事实填满了，就没有编道理的余地。

### 9.5 配套：生成端也要卡一道

材料改好了，还要让生成端**先讲事实再讲判断**。`server/answer.py` 的通用铁律里
已经加了这条（禁止整段由"我会先…""一般我会…"撑起来），经历题的【展开】
也改成"**第一句先说事实**：在哪个项目、具体做了什么、结果是什么"。

⚠ 这两处是配套的：**只改提示词不补材料 = 模型没料可讲，只能更生硬地讲道理。**
材料先补，提示词后改，最后用同一批问题前后对比。

### 9.6 自检：一条命令跑完

```powershell
python tools\deploy_check.py            # 不达标退出码 1
python tools\deploy_check.py --show     # 顺带打印每条答案全文
python tools\deploy_check.py --json     # 机器可读
```

它会用 6 条"经历味"的问题（部署 / 对接 / 工期 / 交付 / 现场定位 / 无真实环境怎么验证）
**真跑一遍快答线**——所以它**会调大模型，不进 CI**，和 `tools/regress.py` 一样属于
"花点钱的手动门禁"。逐条检查四件事：

| 查什么 | 判定 |
|---|---|
| 具体数字 | 【数字】栏不是"无" |
| 具体动作 | 抓字节 / 加了一层 / 灰度 / 最小复现 / 逐字节比对… |
| 环境或对手方 | 客户内网 / 厂商 / 硬件 / 现场 / SITL / 联调… |
| 空话句式 | "我会先…""一般我会…""要分情况看" —— **出现即该条不合格** |

**通过标准**：逐条全过 **且** 含具体数字的条目 ≥ 一半。

实测参考（补完现场材料之后）：

```
逐条通过 6/6 · 含具体数字 4/6（67%，下限 50%）· 空话 0 处
结论: 通过 —— 答案落在"我做过的事"上，材料够用。
```

不通过时它会直接告诉你补哪份材料（`knowledge/_base/现场部署与交付_软件侧实战.md`）。
