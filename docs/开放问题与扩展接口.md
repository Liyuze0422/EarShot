## 一、已知问题（按优先级）

### P0-1｜中文路径下 exe 双击无反应（已缓解，未根治）

- **现象**：安装目录含非 ASCII 字符（中文、日文、带重音的字母）时，双击 `EarShot.exe` 一闪就退，不弹窗、不写日志。
- **定位**：PyInstaller 6.22.3 的 bootloader 在 Python 初始化**之前**用 ANSI 路径打开自身内嵌的 PKG 归档失败
  （`[PYI-...:ERROR] Could not load PyInstaller's embedded PKG archive`）；源码模式的 venv 启动器同样在中文路径下报 `No pyvenv.cfg file`（退出码 106）。实测：同一份 exe 复制到 `C:\EarShot` 就一切正常。
- **已做的缓解（v0.9.23）**：发布包根目录带 `启动-EarShot.bat` + `check_path.ps1` + `README-安装必读.txt`，路径含非 ASCII 时直接中文提示并退出 9；源码 `启动提词器.bat` 也加了同样检测。文档把「安装目录必须纯英文」提为第一条硬要求。
- **根治思路（两条，任选其一并做跨机验证）**：
  1. **验证 PyInstaller 版本回归**：用 6.22.3 与最新版各构建一次，在中文路径跑 `EarShot.exe --version` 对照；若新版已修复 → 升级依赖、重新发版（`tools/release.py` 一条命令）。
  2. **安装器默认释放到纯英文目录**：写一个 `install.bat` / 自解压安装器，默认 `%LOCALAPPDATA%\EarShot`，从源头避开路径问题。
- **验收**：把 exe 放到 `C:\中文目录\EarShot` 下双击，能正常弹出选库窗口（或明确提示并引导迁移）。

### P0-2｜分句：快语速连问仍可能「多问合一」（已拆文本层，音频层留待）

- **现象**：面试官语速快、连续发问时，屏幕只出一条答案；v0.9.23 起文本层会把粘住的多个提问拆开逐条回答，但**音频层的合并仍会发生**。
- **定位**：
  - `server/main.py` 的 `MergeGate`：判停（`vad_end_ms`，默认 600ms）后还会再等 `vad_merge_ms`；窗口内又出声就把两段拼成一段再识别。**实际合并阈值 ≈ 1040ms**（600 + 600 − 起判 160）。
  - 41 场真实面试录音（14.4 小时）离线回放：相邻句界静音 **69.6%（8900/12785）< 1040ms** 会被粘住；合并让「识别单位」少了 **42.4%**（7363 → 4243）。
  - v0.9.23 已把 `vad_merge_ms` 默认降到 350（合并量约 22.2%），并在 `server/extract_q.py` 新增 `split_questions()` 做文本层拆分。
- **修复思路（音频层，P0-3）**：让 `MergeGate` 按「第一段是否完整问句」决定合不合并——判停后先 ASR 第一段，用 `_is_half_sentence` 判断：半句才等合并，完整问句立即发送。需要把 ASR 调用从 gate 之后提到 gate 的判停分支（改动集中在 `server/main.py` 的 `capture_once` 与 `MergeGate`）。
- **验收**：用 `_realdata/` 的真实录音回放，统计「一次 ask 里 ≥2 个独立问题」的比例降到 <3%（现有 7.1% 是人工口径下界）；补 `tests/test_merge_gate.py` 的 500/600/690ms 边界用例。

### P1-1｜VAD / ASR 升级（分句从「能量端点」升级为「语义端点」）

- **现状**：`server/asr_engine.py` 的 `EnergyVAD` 用能量阈值 + 静音 600ms 判停；长句 20s 强制在最安静 300ms 处切。
- **思路**：
  1. 用概率式 VAD（Silero / FSMN-VAD）与能量 VAD 双判据：能量管「有没有人声」，概率管「是不是句末」；
  2. 或换支持**时间戳**的 ASR（Paraformer 流式 / 带时间戳的 SenseVoice），按字级对齐切句；
  3. 端点自适应：短停顿 ≥250ms 且紧邻完整问句 → 早判停。
- **验收**：真实录音回放的「粘连率」显著下降，且首字延迟不明显变差（当前真实面试首字 632~838ms）。

### P1-2｜应用内更新：下载需要断点续传 / 重试

- **现象**：`server/update.py` 的 `_download` 是单次 `urlopen`；国内网络到 GitHub Release 下载 CDN 偶发 SSL 握手超时（v0.9.23 发布后本机实测到 `_ssl.c:983: The handshake operation timed out`），用户点「立即更新」会失败。
- **思路**：加 `Range` 断点续传 + 3 次指数退避重试 + 失败后提示改用全量包；或把更新包同时传一份到可选镜像（用户自配 base_url）。
- **验收**：模拟中途断网，重试后仍能完成校验并装好（校验逻辑 `stage()` 已逐文件 sha256，保底不变）。

### P1-3｜「一题多问」的答案策略 A/B

- **现状**：v0.9.23 拆出的多问是**逐题顺序回答**（前一题答案落屏后才发下一题，二三条会晚几秒）；LLM prompt 仍未针对「多问合一」做逐条回答。
- **思路**：改 `server/answer.py` 的 `build_messages`，当 question 含多个问号时要求「1) 2) 3)」逐条短答；做 A/B（单题 vs 逐条）比较命中率与可念性。
- **验收**：真实日志里多问样本的「应回答但未单独回答」比例下降；答案可念性评分不低于现状。

### P2-1｜非面试/非销售音频过滤（场景门）

- **现状**：9/19 一场游戏直播音频（`logs/session_20260919_175842.jsonl`）的 54 段全部被当作问题回答——router 的正则在非面试语境下几乎全放行。
- **思路**：先判「这段像不像面试」——连续 N 段无「你 / 请 / 介绍一下 / 问」等特征 → 提示「没听到提问」或静音，不调用 LLM；或用 `logs/` 里 288 条 answer + 1145 条 filtered 做轻量分类器。
- **验收**：非面试音频的误答率降到 <10%，真问题召回不降。

### P2-2｜启动速度（当前就绪约 30~36 秒，大头是预热）

- **现状**：`server/main.py` 的 `boot()` 分段计时：模型加载 8.2s、**预热识别 30.8s**（numba JIT 首次编译）、建索引与答题预热累计约 35.7s。
- **思路**：把 numba 编译缓存到磁盘（`NUMBA_CACHE_DIR`）、把预热移到后台（先放行 `/healthz` ready，预热期间首题降级）、索引按知识库哈希缓存到磁盘做增量。
- **验收**：冷启动到 ready <20s，首题出字延迟不明显变差。

### P2-3｜源码模式 venv 重建

- **现状**：仓库 `.venv` 是指向旧目录的 junction，中文路径下报 `No pyvenv.cfg file`（同 P0-1）；源码模式暂时只能用「系统 Python + PYTHONPATH 指向 .venv site-packages」绕。
- **思路**：在纯英文路径重建 venv（`python -m venv .venv` + `pip install -r requirements.txt`），删掉 junction；README 补充说明。
- **验收**：`启动提词器.bat` 在纯英文路径下能直接起后端 + 浮窗。

### P3｜销售对客版本（手机采集 + 电脑协同）——设计已留，未实现

- 见 **[销售对客版本_预留设计.md](销售对客版本_预留设计.md)**（802 行完整设计：手机采集端 / 协同通道 / 销售对客逻辑引擎 / 合规门禁 / MVP 里程碑）。
- 核心结论：**复用面试版约 70%**（VAD/ASR/检索/LLM/浮窗/事件协议/更新机制）；新建手机采集端 + 局域网协同（WS + Opus + 二维码）+ 销售逻辑引擎。
- 最大风险：**合法地拿到干净的客户声音**——To C 走通话耳机模拟分线或第二设备近场拾音；To B 走 CTI/SIP 双声道 RTP（最优）；iOS 通话录音**不承诺**，Android 10+ 也抓不到 VOICE_COMMUNICATION。

## 二、可扩展接口清单（不改核心代码就能接）

### 2.1 配置层（`config/settings.json`，全部有默认值）

| 键 | 作用 | v0.9.23 默认 |
|---|---|---|
| `vad_end_ms` | 判停静音时长 | 600 |
| `vad_merge_ms` | 判停后合并窗口 | 350 |
| `split_multi_q` / `split_multi_q_max` | 文本层多问拆分开关 / 上限 | true / 3 |
| `hold_incomplete` / `max_hold_s` | 半句暂存与超时 | true / 4.0 |
| `asr_textnorm` | ASR 标点归一化（拆多问依赖 withitn） | withitn |
| `corpus_globs` / `corpus_profile` | 知识库目录 / 资料包 | 见配置手册 |
| `ports` / `base_url` / `llm_model` | 端口 / LLM 端点 / 模型 | 8765~8769 / DeepSeek / deepseek-flash |
| `dsh_node` / `dsh_bin` / `dsh_home` | 可选深答线（外部 agent） | 空 = 关闭 |

环境变量优先：`TP_MODEL_DIR`、`TP_API_KEY`、`TP_CORPUS_GLOBS`、`TP_CORPUS_PROFILE` 等，见 `docs/配置手册.md`。

### 2.2 规则扩展点（纯正则/词表，改完跑测试即可）

| 文件 | 扩展什么 |
|---|---|
| `server/router.py` | `SKIP`（非提问）、`DESIGN`、`BEHAVIOR`、`MOTIVATION`、`REVERSE`、`QUESTION_FORM`、「长句末尾强疑问」表 |
| `server/extract_q.py` | 问题抽取锚点、`_META`（面试官自述）、`_PREMISE`（前提词）、`split_questions` 的从句合并规则 |
| `server/termfix.py` | 术语纠错（中文按 jieba 词频判、英文按 token） |
| `server/bank.py` | 题库兜底、追问预案 |
| `config/known_terms.md` / `never_used.md` / `domain_words.txt` / `topic_terms.json` | 词表与话题映射（数据层扩展，零代码） |

### 2.3 组件替换点（类/函数边界清晰）

| 模块 | 替换目标 | 接口约定 |
|---|---|---|
| `server/asr_engine.py` 的 `EnergyVAD` | 换成任意 VAD（Silero/FSMN） | `feed(block) -> (state, audio)`，state ∈ {idle, speech, end} |
| `server/asr_engine.py` 的 `SenseVoiceASR` | 换 ASR 模型 | `.transcribe(audio) -> (text, seconds)`；`.warmup()` |
| `server/answer.py` 的 `build_messages` / `answer_stream` | 换 LLM / Prompt 策略 | 流式回调 `on_delta` + `should_stop`；返回 (text, first_s, total_s, qtype, hits) |
| `server/main.py` 的 `emit()` 事件 | 接自己的 UI / 手机端 | WebSocket JSON 事件，见 `ui/app.py` 的消费侧 |
| `ui/app.py` | 换浮窗形态 | 只依赖 `/ws` 事件协议与 `.runtime_port` |

### 2.4 场景抽象建议（面试 / 销售 / 客服共用一个内核）

现有架构的「采集 → VAD → ASR → 抽取/分类 → 检索 → LLM → 浮窗」与场景无关，真正随场景变的是四样东西：

1. **语料**（`knowledge/` + `corpus_profile`）；
2. **分类规则**（`router.py` 的策略表）；
3. **答案/提示策略**（`answer.py` 的 prompt 模板 + `bank.py` 的兜底题库）；
4. **输出契约**（面试版是「一段可照念的答案」；销售版是「下一步动作卡」）。

建议把 2/3/4 外置成 `profiles/<场景>.json`（规则表 + prompt + 卡片模板），`main.py` 启动时按 `corpus_profile` 加载——这就是销售对客版本最省力的接入方式。

## 三、参与方式

```powershell
# 环境（注意：安装/仓库路径必须纯英文，见 P0-1）
git clone https://github.com/Liyuze0422/EarShot.git C:\dev\EarShot
cd C:\dev\EarShot
python -m venv .venv ; .\.venv\Scripts\Activate.ps1
pip install -r requirements.txt
python tools\download_model.py

# 提 PR 前的门禁（与 CI 一致）
ruff check .
python -m pytest -o addopts= -q
python -m pytest -o addopts= -q tests/test_repo_hygiene.py
```

- 改动涉及延迟/准确率：PR 里贴**改动前后的实测数字**与跑测命令（项目风格见 `docs/性能实测.md`）。
- 涉及 `docs/` 的改动：跑 `powershell -File scripts\sync_wiki.ps1`，否则 hygiene 扫 `wiki/` 会挂。
- `.bat` 必须 ASCII-only + CRLF；`.ps1` 必须 UTF-8 带 BOM + CRLF（中文 Windows 的坑，见 `AGENTS.md`）。

## 四、交接时的隐私红线（不要违反）

- **不要提交**：`knowledge/`（除 `README.md`）、`config/`（除 `*.example.*`）、`logs/`、`_realdata/`（真实面试录音）、`models/`、`config/api_key.txt`、`tests/real_questions.json`。
- **不要出现真实公司名/人名**（包括 CHANGELOG、注释、示例、issue 截图）；`tests/test_repo_hygiene.py` 会拦。
- 用 AI 整理自己的语料时，注意先脱敏（见 `docs/喂给AI的面试资料整理提示词.md` 的「脱敏」约定）。
- 发版（`tools/release.py --build --publish`）需要 `gh` 登录；大文件上传失败时，先创建已发布 Release，再逐个 `gh release upload`（v0.9.23 发布时踩过：直传 231MB 全量包会 404 并回滚 Release）。

## 五、作者留给接手者的话

- 这个项目最值钱的两件事：**「不编」**（材料里没有就坦诚说）+ **「本地优先」**（除了 LLM 调用，全部在本机）。任何改动都不该破坏这两条。
- `docs/性能实测.md` 里标了「诚实边界」的每一节，都是实测过的坑，不要用猜测推翻它们。
- 语料决定体验：同一个人、同一个岗位，材料整理得好坏能让 hit@1 差一倍（89.7% vs 41.0%）。如果只做一件事，就做「让用户更容易把语料填对」——v0.9.23 的 `docs/喂给AI的面试资料整理提示词.md` 是这条路的起点。
