# EarShot（顺风耳）· 性能实测

> 本文件只记录**跑出来的数字**。
> 数据来源：本项目开发期的本机实测记录（原始记录为 `进度.md` 与 `测试报告_真实一面回放.md`，均注明“本机实测，非估算”）。
> 测试机：Windows 桌面机（RTX 3060 6 GB）；ASR 走 **CPU 纯 int8 ONNX**，未使用 GPU；DeepSeek 走公网 API。

## 口径说明（先看这一段）

| 标注 | 含义 |
|---|---|
| **实测** | 在本机真实跑出来的数（含脚本名与批次的见各表脚注） |
| **换算** | 由实测值相加得到的端到端预算，不是一次单独的测量 |
| **目标 / 预估** | 设计阶段定的验收线或对硬件的估计，**未逐条验收**，不当作实测 |
| **待补** | 无记录，本文不臆测 |

另需注意三个批次口径不同，不要混着比：

1. **单机抽样**：开发过程中随机几句的真实调用（数字区间宽，含网络抖动）。
2. **真实一面回放**：拿 2026-08-31 那场真实一面的逐字转写当测试集，人工筛出 **44 条真实提问 + 6 条非提问**，另加 14 条合成题。**输入是文本，不含 VAD 判停与 ASR**，等于“从提问到答案”的纯生成段。
3. **端到端预算**：把各环节实测值相加，得到“面试官说完 → 第一行答案上屏”。

## 一、音频链路

| 项目 | 值 | 类型 | 备注 |
|---|---|---|---|
| 采集方式 | WASAPI 回环（渲染流） | 实测 | 只抓系统播放的声音＝面试官，不碰麦克风 |
| 回环设备 | `耳机 (Realtek(R) Audio)` | 实测 | **默认设备是耳机，回环照样可用** |
| 系统内其它回环设备 | 扬声器 / 耳机 / 入梦扬声器 (VB-Audio Cable A) | 实测 | 共 3 个候选 |
| 采集格式 | 16000 Hz 单声道，20 ms 一帧（320 采样） | 实测 | 设备侧按默认扬声器取回环 |
| 抓到的 TTS 音频强度 | RMS 0.0837，峰值 0.870 | 实测 | 模拟面试官语音，信号强度充足 |
| VAD 起判 | 连续 160 ms 超阈值 | 实测 | 不是单帧触发 |
| VAD 阈值 | 启动按底噪自动标定，钳在 0.004~0.02 | 实测 | 写死 0.006 会在音量小/环境吵时失效 |
| VAD 判停（句末静音） | **600 ms** | 实测 | 激进模式可调 300 ms，未作为默认 |
| 单段最长 | 20 s（到点在最近最安静的 300 ms 处切开） | 实测 | 故障注入：200 块音频切 4 段，样本数一个不丢 |
| 采集自愈 | 异常后退避 1 s → 15 s 重连；每 5 s 检测默认设备变化 | 实测 | 故障注入：连续两次异常后 audio_lost → audio_reconnecting |

> 采集环节的“音频丢帧率 / 静音段占比”**待补**（没有单独统计）。

### 检索的真实边界：六个被否定的改法（2026-09-13）

背景：39 条 GOLD 上还有 4 条 hit@1 未中（#4 / #26 / #38 / #39），其中 #38 / #39 连 top-3 都没进。
为了补这最后 2 条，把能想到的改法逐个实测了一遍 —— **六个全是否定的**。
写在这里是为了以后别再重复试。

| # | 改法 | 结果 |
|---|---|---|
| 1 | 用检索分数当置信度 | **不行**：`RRF_SCORE_SCALE = RRF_K`，只开词级通道时排第 1 恒等于 60/61=0.9836。分数只是排名的函数，不含任何独立信息 |
| 2 | 用「查询词被 top-1 覆盖了多少（IDF 加权）」当置信度 | **方向是反的**：命中的中位 0.181，未命中的中位 **0.276**；top-3 覆盖 0.321 vs **0.637** |
| 3 | `HR_HINT` 去掉 `角色`/`占比` | **零变化**（89.7/94.9）。原因：继承门用的是同一个正则，拿掉后门跟着开，把上一题（HR 题）的材料又拖回来 —— 两个机制互相补偿 |
| 4 | 查询窗口里剔除 HR 句 | **零变化**。HR 词本来就在当前句里（"还有哪些**角色**"） |
| 5 | HR 加权从 3.0 调小到 1.5 | **零变化**；调到 1.0 反而把 #36/#37/#46 一起打掉（82.1/87.2） |
| 6 | sticky 判定用更严的 HR 正则（继承门保持关闭） | **更差**：只留强标记时 87.2/92.3，#37 也跟着丢 |

**为什么补不上**（这是结论，不是借口）：

- **#38「还有哪些角色呢？你在里面承担哪一种？」** 的期望材料是 项目1，但这句话的字面词
  （角色 / 承担）在 HR 材料里更密集。同样一句「还有哪些角色」在 HR 场景下完全是合理提问。
  **要分开得靠语义，靠词表/权重分不开。**
- **#39「整个架构或者整个功能来说，你做的占比估计有多少？」** 同理：`占比` 既是 HR 词也是项目词。
- **#4「在暂时吗？」是 ASR 听错**（原话大概率是「在准备吗 / 还在吗」），检索层救不了转写错误。

**顺带纠正上一版的一个说法**：下面「其余负面结果」里写「不加 HR 守卫时 '占比多少/同一家公司'
会让 hit@3 掉 3 条」。今天逐条量出来：加守卫（现状）hit@3 = 94.9%，**#39 恰恰是被守卫害的**，
而完全不认 HR 是 82.1/87.2。也就是说守卫整体是正收益（+7.6 hit@1），
但「占比」这个词归类到 HR 是它的**代价**，不是收益。原话不够准确，以此处为准。

### 第七个否定结果：拿话题词表当绕法（这条差点被我写进文档）

在上面六个都失败之后，我给 README 写过一条「短期绕法」：把 `角色`/`占比` 补进对应项目的
`config/topic_terms.json`，让 `detect_topic` 直接命中项目而不是 HR。**写之前先测了一遍，结论是没用**：

| 往「项目1」的话题词追加 | hit@1 | hit@3 | 未中明细 |
|---|---|---|---|
| 不追加（现状） | 89.7% | 94.9% | #4(仅3) #26(仅3) #38 #39 |
| +角色 +占比 | 89.7% | 94.9% | 不变 |
| +角色 +占比 +承担 | 89.7% | 94.9% | 不变 |
| +角色 +占比 +承担 +架构 +功能 | **92.3%** | 94.9% | #4(仅3) #38 #39 |

- 只加「角色/占比」**一分不动**：即使话题判定切到了项目，HR 材料的 BM25 原始分仍然更高，×3 也压不过去。
- 唯一有提升的那一行靠的是「架构/功能」这类**泛词**，而它修的是 **#26**（另一条题），不是 #38/#39。
  泛词放进话题词表意味着任何一句带「功能」的话都会触发项目加权 —— 真实面试里会到处误触发，
  **收益与风险都没验证**，所以不建议这么做。
- 教训：**给用户的建议也要过一遍实验**。这条如果直接写进 README，用户照着改会发现毫无变化，
  然后开始怀疑是不是自己配错了。

---
### 未定论：来源多样性（不能算数）

观察：top-3 经常整整齐齐来自**同一份文件**（#38 就是 HR,HR,HR）。同一份材料的 3 块内容高度重叠，
对模型是冗余的。试了「每个文件最多留 N 块」。

结果 **不可比**：为了让多样性有候选可挑，必须让检索返回更宽的池子（topk 12），
而 RRF 的分数依赖排名，池子一变，排名跟着变 —— 宽池基线自己就只有 92.3%，
不是生产的 94.9%。宽池内比较是 92.3% → 94.9%，但**不能拿它和生产的 94.9% 相减**。
要真正验证得改 `search` 的取候选方式再重测，目前证据不足以采纳，**默认行为不变**。

| 全量回放 | 44 条 **0 次失败**，78 秒跑完 | 实测 | 会真调模型 |

| 场景 | 第一题墙钟出字 | 第二题 |
|---|---|---|

## 七、未验证的部分（不要当成已验证）

来自真实一面回放测试报告的“这次没覆盖到的”一节，以及后续几轮的诚实边界：

| 项目 | 状态 | 说明 |
|---|---|---|
| **ASR 在真实面试音频上的准确率** | ❌ 未测 | 手上只有逐字转写稿，没有原始录音；TTS 回环只是代理验证 |
| **深答线（外部 agent 子进程）** | ❌ 未进回归 | 只有旧记录里的 **31.6 s**；本轮未测。该能力现在是可选项（`dsh_node` / `dsh_bin` / `dsh_home` 三项都填才启用），默认关闭，因此不影响主链路 |
| **行为面试题** | ⚠️ 覆盖不足 | 真实一面 **0 条**行为题，只用 14 条合成题覆盖 |
| **路由 100% 的泛化能力** | ⚠️ 拟合上限 | 规则照同一场数据调的，换一场必然下降 |
| **屏幕共享不可见 / 置顶** | ✅ 上一轮已验，本轮未动 | 本轮回归没有重跑这两项 |
| **话题持久化的过拟合风险** | ⚠️ 未量化 | 这场面试 90% 时间聊同一个项目；换一场若面试官在多个项目间横跳、新话题又不在词表里，可能帮倒忙（只有一个常量可退） |
| **多人混轨** | ❌ 未解决 | 转写里分不清面试官在问谁 |
| **整句没有实词的追问** | ❌ 未解决 | 39 条里还剩 3~5 条检索不到（#26/#38/#39，“还有哪些功能 / 哪些角色 / 占比多少”），只能靠题库覆盖 |
| **中文专名的 gap 判定** | ⚠️ 按设计不判 | “知识图谱”“强化学习”这类成分常见的复合词宁可漏报 |

| **核心句 ≤40 字** | ⚠️ 74% | 短确认题的核心句天然偏长，指标本身对这类题不适用 |
| **浮窗内存 / CPU 占用** | 待补 | 只测了后端进程（491 MB） |
| **长会话稳定性（>1 小时连续运行）** | 待补 | 无记录 |

## 八、怎么复现

```powershell
# 会前全链路自检（10 项；--fast 约 7.6 s，默认约 21 s）
python tools/preflight.py --fast

# 回归门禁（9 项，含故障注入与离线判据）
python tools/regress.py
python tools/regress.py --quality 10        # 抽 10 条真实提问真跑 + 判分（会真调模型）

# 分项基准
python tools/bench_model.py                 # ASR 单次识别 / RTF / 内存
python tools/bench_material.py              # 检索索引与单次检索
python tools/bench_gap.py                   # gap 判据耗时
python tools/compare_before_after.py        # 改造前后对比

# 真实一面回放（44 条真实提问，会真调模型）
python tools/e2e_smoke.py
python tools/judge_answers.py               # 答案质量判分

# 面试后复盘（读 logs/session_*.jsonl 出报告）
python tools/session_report.py
```

**换一场面试必须重跑**：`tools/regress.py`（路由与话题持久化都是在本场数据上调的）、`tools/test_gap_fp.py`（名词判据）、`tools/build_bank.py`（题库）。
