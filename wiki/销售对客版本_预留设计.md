# 顺风耳 · 销售对客版（EarShot-Sales）架构设计

> 版本 v0.1 ｜ 2026-11-21 ｜ 状态：**预留设计 / 不实现代码**
> 基线：EarShot 0.9.x（实时面试提词器，Windows 单机）｜ 作者：架构组（sales-architect）
> 定位：同一套「听 → 转写 → 检索 → LLM → 浮窗」骨架，把场景从「面试问答」换成「销售对客通话」

> 标注约定：
> - **[实测]** 来自现有仓库 docs/性能实测.md 的真实跑数；
> - **[公开资料]** 有外链依据（见附录 E）；
> - **⚠ 估算** 本项目未实测，仅用于预算与排序，**不得当成验收线**；
> - **〔待确认〕** 需要产品/法务/客户方拍板的假设（汇总在第 8 节）。

## 0. 一页结论

1. **骨架可复用约 70%**。采集之后的整条链路（VAD 判停 → SenseVoice ONNX 识别 → 规则抽取/分类 → BM25 检索 → LLM 流式改写 → PyQt6 浮窗）输入都是「一段 16kHz 单声道语音」和「一段文本」，**与场景无关**，可直接搬。真正要动的只有三处：音频来源、提示策略、合规门禁。
2. **新建的只有四块，但每一块都不小**：手机采集端、协同通道、销售对客逻辑引擎、多人/通话场景适配；外加一个横切的合规子系统。
3. **最大风险是「拿不到干净的客户声音」**。Android 10+ 第三方 App 抓不到通话音频（AudioPlaybackCapture 默认不捕获 USAGE_VOICE_COMMUNICATION）；Google Play 自 2022-05-11 起明令 Accessibility API 不得用于远程通话录音；iOS 没有任何公开 API 能录制蜂窝通话（Apple 官方论坛原话："There's no supported API to record voice calls managed by other apps (including the built-in Phone app)."）。所以「手机 App 后台静默录通话」**不能作为产品承诺**。
4. **因此推荐双轨**：
   - **To C（个人销售，MVP）**：只采**客户侧**音频 —— 通话耳机输出做**模拟分线**拾音，或企业话务旁路；退路是「手机免提外放 + 第二设备近场拾音」，接受混轨。
   - **To B（销售团队，终局）**：接企业 CTI / SIP / 云呼叫中心，直接拿**双声道 RTP**（左坐席、右客户）—— 无权限障碍、天然说话人分离、合规最干净、延迟最低。
5. **延迟目标**：客户说完 → 第一张提示卡上屏 **P50 ≤ 1.5 s、P90 ≤ 2.2 s**（复用面试版 1.3~1.5 s 实测骨架 + 手机链路约 0.1 s）。价格/参数这类**结构化卡不走 LLM**，可压到 **≤ 1.0 s**，且 0 幻觉。
6. **一条产品红线**：销售场景里「报错价」和「承诺没做出来的功能」的后果，比面试场景「编一段经历」更重（法律 + 商业双重）。**LLM 永远不允许生成数字**，报价只能由价格表模板填充；越权折扣直接变「需请示」卡。

### 关键决策一览

| # | 决策点 | 结论 | 放弃的备选与理由 |
|---|---|---|---|
| D1 | 采哪一侧的声音 | **只采客户侧**（分线 / CTI 下行）为第一优先；混轨作为降级 | 手机麦克风直录必然混入销售自己的声音，需做分离，成本高且不稳 |
| D2 | 手机传音频还是传文本 | **MVP 传音频**（Opus 16kHz），PC 端 ASR | 文本上行（手机本地 ASR）留作「高隐私模式」，不进 MVP（见 3.6） |
| D3 | 协同通道 | **局域网 WebSocket + Opus 二进制帧 + 二维码配对** | WebRTC 复杂度高、蓝牙带宽/协议不支持、云中继作为跨网降级 |
| D4 | 配对方式 | **二维码**（携带 IP:Port + 一次性 token + 证书指纹） | mDNS/广播常被企业 Wi-Fi 禁用；手动输 IP 易错 |
| D5 | LLM 位置 | **PC 端调云 API**（默认），预留本机小模型 | 手机端调 LLM 要管密钥、要屏幕也没用；全本地模型质量换稳定性 |
| D6 | 价格怎么出 | **结构化模板填充，0 LLM** | 让 LLM 参与报价 = 必然出现数字幻觉，不可接受 |
| D7 | 分发 | Windows 安装包复用；Android 走侧载/企业 MDM；iOS 只做「辅助端」不承诺通话录音 | 上架 Google Play 与通话录音能力互斥 |

## 1. 结论先行：复用、新建、最大风险

### 1.1 与面试版的本质差异（先看清，再谈复用）

| 维度 | 面试版（现状） | 销售对客版 | 对架构的影响 |
|---|---|---|---|
| 音频来源 | WASAPI 回环，**只抓对方** | 手机通话，**天然混轨**或需硬件分线 | 采集层整体新写 |
| 说话人 | 天然只有面试官，不需要分离 | 销售 + 客户（+ 可能多个客户） | 新增说话人/角色标注 |
| 输出目标 | 一段**可照念**的答案 | 一张**下一步动作**卡（问什么/怎么答/别说什么） | 输出契约从「答案」变「卡片」 |
| 允许打断 | 说完就推，越快越好 | **不许抢话**，时机 > 速度 | 新增提示调度器 |
| 准确性红线 | 不编经历、不编数字 | 不报错价、不承诺功能、不触禁用话术 | 数字校验从「提示」升级为「硬拦截」 |
| 合规 | 使用者自担（面试方可能禁止） | **必须双方知情**，否则产品不成立 | 新增合规子系统（硬门禁） |
| 部署 | Windows 单机 | Windows + Android（+ iOS 辅助）+ 网络 | 新增配对/传输/后台存活 |
| 生命周期 | 30~60 分钟一场 | 5~40 分钟一通，一天多通 | 会话边界、留存、审计节奏都不同 |
| 失败代价 | 答砸一题 | 吓跑客户 / 报错价 / 违法 | 风险预算更高，宁可不出卡也不出错卡 |

### 1.3 新建清单（四块 + 一个横切）

1. **手机采集端 App**：音频采集、Opus 编码、本地省流 VAD、断网环形缓存、前台服务/后台存活、二维码配对、TLS 证书固定、电量策略、通话状态监听。
2. **协同通道**：PC 侧接收服务（局域网 WS 或云中继客户端）、jitter buffer、丢包/抖动统计、重连与会话恢复、配对与鉴权。
3. **销售对客逻辑引擎**：语料 schema、结构化产品/价格库、话语行为分类、提示状态机、优先级调度器、卡片组装（模板 + LLM 两条路）、置信度与人工确认、采纳埋点。
4. **多人/通话场景适配**：说话人/角色标注（CTI 双声道优先，单声道用能量+声纹近似）、「销售自己正在说话」检测、多客户场景、打断重叠检测。
5. **合规子系统（横切）**：双方告知与同意记录、采集开关硬门禁、加密与留存策略、PII 脱敏、出网守卫、审计日志、一键清除。

### 1.4 最大风险（按影响排序）

| 排名 | 风险 | 为什么是最大 | 触发后果 |
|---|---|---|---|
| 1 | **手机端拿不到干净通话音频** | 操作系统权限 + 商店政策 + 机型差异三重限制，不是工程能绕过的 | 产品退化成「双设备声学拾音」或「企业专线」，To C 市场空间大幅缩小 |
| 2 | **合规不接受**（未经客户明确同意） | 民法典 1033 条：除法律另有规定或权利人明确同意外，不得窃听他人私密活动 | 产品不得上线 / 上线即下架 / 民事或行政责任 |
| 3 | **客户反感**（发现被录音/被提示） | 对客场景里信任是成交前提，被发现一次就丢单，且会传播 | 口碑崩塌，To B 采购直接否决 |
| 4 | **报错价 / 承诺未实现功能** | 商业与法律双重后果，且销售会**直接照念**（比面试更依赖屏幕） | 合同纠纷、赔偿、内控处罚 |
| 5 | **不抢话做不到**（提示来晚了或来早了） | 提示本身会干扰对话节奏，用户体验是生死线 | 销售关掉产品 |

> 一句话：**这个产品 80% 的难点不在 AI，在「合法地拿到声音」和「不多嘴」。**

### 2.2 需新建组件的职责与接口（预留设计，不实现）

**A. 手机采集端（Android 优先）**

职责：采集 → 编码 → 传输 → 断线缓存；不含任何业务逻辑。

    模块            职责                                     关键约束
    AudioSources    选择音源：麦克风 / 通话下行分线 / 系统录音文件  机型能力差异必须在运行时可探测
    Preprocess      降噪、AGC、48k→16k 重采样、20ms 分帧       手机 AEC 会引入 10~20ms 额外延迟
    OpusEncoder     16kHz 单声道、24kbps、20ms 帧、FEC         帧序号 + 时间戳必须单调，用于 PC 端对齐
    GateVAD         本地能量门限，静音不发送（省流省电）        只做「省流」，不做「判停」（判停在 PC，避免双端不一致）
    RingBuffer      断网时缓存最近 N 秒（建议 10~30s）           重连后补传并打「补传」标记
    Transport       WS/TLS 客户端，自动重连                    证书指纹固定 + 一次性 token
    Pairing         扫二维码、显示 4 位校验码、会话绑定          扫码 → 直连 → 失败 → 中继提示
    ForegroundSvc   麦克风类型前台服务 + 常驻通知 + 电池白名单引导   Android 14+ 必须 while-in-use 启动
    CallState       通话状态监听、免提/耳机路由变化、AudioFocus 丢失  路由变化需重选音源

**B. 协同通道（PC 侧）**

职责：接收、缓冲、解码、交给 VAD/ASR；统计与告警。

    模块             职责                                        关键指标
    LanWsServer      局域网 WS（TLS），端口候选顺延，单实例守卫      复用面试版端口/单实例思路
    RelayClient      云中继客户端（可选，E2E 加密，中继只见密文）    跨网场景
    JitterBuffer     3~6 帧自适应（40~120ms），按 RTP/seq 重排      抖动 P95 目标 ≤ 30ms
    Decoder          Opus → PCM 16k mono                        解码 ≤ 2ms/帧
    NetStats         丢包率、RTT、抖动、重连次数                   每秒上报，UI 显示「链路健康」
    SessionGuard     token 一次性、设备指纹、重复连接拒绝           防串流/防重放

**C. 销售对客逻辑引擎（PC 侧，新核心）**

职责：把「客户这句话」变成「销售下一步该做什么」。

    模块               职责                                     输入 → 输出
    UtteranceClassifier 话语行为分类（8 类）                      ASR 文本 → label + 置信度
    StageTracker        六阶段状态机（寒暄/挖需/方案/异议/逼单/收尾）+ 异常态   label 序列 → 当前阶段 + 证据
    CardRouter          结构化精确匹配 vs BM25 语义召回           文本 → 候选卡集合
    CardComposer        卡片组装：模板卡（0 LLM）/ 生成卡（检索+LLM）  候选 → 卡片对象
    PriorityScheduler   打分 + 硬规则 + 时机门控                   卡片集合 + 说话状态 → 推哪些、何时推
    ConfidenceGate      置信度分档与人工确认                       卡片 → 主卡/副卡/抽屉
    RedlineGuard        价格/承诺/禁用话术硬拦截                    卡片 → 放行/替换/拦截
    FeedbackStore       采纳/忽略/纠错埋点（不含原文）              点击 → 指标
    AuditLog            谁、何时、看了什么卡、有无越权               全链路可追溯

**D. 多人/通话场景适配**

    能力                实现路径                                             MVP 是否必须
    说话人分离          CTI 双声道（首选）/ 单声道能量+近远场规则+可选声纹注册     是（否则「不抢话」做不准）
    销售侧活动检测       PC 麦克风「只算能量、不转写」（隐私可解释）            是
    重叠说话检测        双声道同时高能量 → 提示「等客户说完」                   是（低成本高收益）
    多客户              只做「非销售说话人」聚合，不区分具体是谁                否（Phase 2）
    打断/抢话抑制        见 6.6 硬规则                                        是

### 2.3 不可复用 / 必须承认失效的部分

- **WASAPI 回环采集**：手机通话的声音不在 PC 的渲染流里，彻底失效。
- **「天然区分说话人」这个白拿的优势**：这是面试版最省事的一步，销售版**必须自己解决**（见 2.2 D、6.4）。
- **「答案可照念」的输出契约**：销售版照念会显得机械，输出要改成**动作提示 + 一两句可选用的话**。
- **冒烟测试的假设**：现有 tests/ 的很多用例建立在「回环 + 单说话人」上，销售版需要独立的测试基线。

### 3.4 延迟预算的瓶颈分析

| 环节 | 占端到端比例 | 能不能压 | 怎么压 |
|---|---|---|---|
| **VAD 判停 600 ms** | ~41% | 能，但有代价 | 调到 400ms 可省 200ms，但客户换气会被切句 → 两次出卡、答案各答一半（面试版已实测过这个坑）。**销售场景建议不降反升到 650ms**，用「预出卡」弥补（见 6.6） |
| **LLM 首字 616 ms** | ~42% | 能，收益最大 | ① 价格/参数/条款/案例 → 结构化模板，**0 LLM，整段消失**；② 异议应答先出「结构化骨架卡」（0.8s 内），再用 LLM 补「一句话措辞」；③ 裁剪上下文（top-2 材料、去掉 company.md 全文）；④ 本机小模型只做「选卡」不做「写句子」 |
| 手机链路 110~190 ms | ~10% | 能，小幅 | USB 网络共享/手机热点替代 Wi-Fi；jitter buffer 自适应下限收到 40ms；关闭手机端 AEC（只采客户侧，不需要回声消除） |
| ASR 100 ms | ~7% | 不太能 | 已 RTF 0.025~0.03 [实测]，再快意义有限；换流式 ASR 可做「边说边出半句」，但那是**新增能力**，不进 MVP |
| PC 内部其余（检索/状态机/渲染） | <3% | 不必 | 合计 <30ms |
| 网络异常尾部 | 尾部风险 | 必须兜底 | 断流时 UI 明示「链路中断」，并自动降级为离线话术卡（本地题库），绝不静默 |

**结论：延迟不是这个产品的主要矛盾，「出卡时机」才是。** 1.5s 对「客户刚说完、销售正在组织语言」这个空档是可接受的；但如果是客户**还在说**就弹卡，哪怕只快 100ms 也是负分。所以预算是双目标：**P50 ≤ 1.5s 且「抢话率」≈ 0**。

### 3.5 为什么电脑端做 ASR/LLM，而不是手机端

| 维度 | 手机端做 ASR | PC 端做 ASR（本设计） |
|---|---|---|
| 端到端延迟 | 低端机 RTF 可能 >0.3（积压）；高端机约 100~200ms，**并不比 PC 快**，而 PC 实测 80~115ms | 100 ms [实测]，稳定 |
| 资源 | +230MB 模型 + ONNX Runtime + 500MB 级内存；发热、掉电、后台被杀 | 后端 491MB 内存 [实测]，插电机器无压力 |
| 安装包与分发 | APK 体积 +150MB 起，商店审核与模型分发都更麻烦 | 沿用现有 Windows 安装包 |
| 一致性 | 多机型多版本模型，纠错词表/评测集要同步维护 | 一套模型、一套词表、一套评测（termfix/regress 都在 PC） |
| 隐私 | 音频不出手机（略优） | 音频仅在**自己局域网**内传给自己的 PC（TLS 加密） |
| 带宽 | 传文本 ~200B/句（最优） | Opus 24kbps ≈ 3KB/s ≈ 10.8MB/小时 ⚠ 估算（可接受） |
| 失败面 | 每个机型都是新问题 | 只有一台 Windows 要调 |
| 检索/LLM | 无论如何都在 PC（知识库、密钥、屏幕都在 PC） | 天然 |
| 结论 | 只作为「高隐私模式」预留（客户禁止音频出设备时） | **MVP 默认** |

补充：手机端仍然要做**本地能量门控（GateVAD）**——静音帧不发，省 60~70% 带宽与电量；但**判停（endpointing）放在 PC**，避免两端判定不一致导致「半句话」。

## 4. 手机-电脑协同方案

### 4.1 方案对比

| 方案 | 时延(P50) | 跨网 | 弱网/丢包 | 隐私 | 配对/运维 | 端侧依赖 | 结论 |
|---|---|---|---|---|---|---|---|
| **局域网 WebSocket + Opus** | **+65~90ms** | 否（需同网段） | TCP 重传会累积延迟，需应用层 jitter buffer | 高（不出局域网，TLS 自签 + 指纹固定） | 二维码一次性配对，简单 | Android/iOS 均可自研 | **✅ 首选（MVP）** |
| WebRTC（P2P / 局域网） | +50~80ms | 需 STUN/TURN | **最好**（NACK/FEC/自适应码率/自带 jitter buffer） | 高（DTLS-SRTP） | 信令服务器 + ICE 复杂度高 | Android 有成熟 SDK；PC 侧 Python 生态弱（aiortc 可用但调优成本高） | ⏳ Phase 2（跨网刚需时） |
| WebRTC over TURN（云中继） | +150~300ms | **是** | 好 | 中（中继可见元数据，媒体 DTLS 加密） | 要运维 TURN | 同上 | 备选 |
| **云中继 WebSocket（E2E 加密）** | +80~250ms | **是** | 中（可自动重连 + 环形缓存补传） | 高（中继只见密文，密钥经二维码带出） | 要部署中继 + 计费 | 自研，简单 | **✅ 跨网降级首选** |
| 经典蓝牙（SPP/HFP） | +50~200ms | 点对点 | 差 | 高 | 配对麻烦 | **HFP 被通话应用独占，第三方取不到通话音频**；A2DP 只有媒体 | ❌ 不可行（只可用于配对/控制） |
| BLE | 音频带宽不足 | 点对点 | 差 | 高 | 需 LE Audio | Android/iOS 支持 LE Audio 的机型有限 | ❌ 不用于音频 |
| USB 网络共享 / adb reverse | **最低（<20ms）** | 否（有线） | 极好 | 最高（物理直连） | 需要用户手动开 | Android 原生支持；iOS 个人热点可用 | ✅ **备用/演示环境**（现场调试最稳） |
| 二维码 | — | — | — | — | — | — | **不是传输，是配对层**（所有方案都用它） |

### 4.2 推荐架构（分层）

    第 0 层  配对层     二维码（IP:Port + 一次性 token + 证书指纹 + 协议版本）+ 4 位校验码
    第 1 层  传输层     局域网 WS/TLS（默认）→ 云中继 WS/E2E（跨网）→ USB 网络共享（现场）
    第 2 层  媒体层     Opus 16kHz 20ms 帧 + 序号 + 时间戳 + FEC；静音门控（省流）
    第 3 层  会话层     会话 ID、心跳 1s、背压、断线环形缓存（10~30s）、重连补传
    第 4 层  控制层     pause/resume、标记时刻（mark_moment）、音量/增益、关闭采集（合规）

### 4.3 推荐拓扑（MVP，避开企业 Wi-Fi 的坑）

    手机（开热点，2.4G/5G） ──── PC 连接该热点 ──── 手机 App 直连 192.168.43.x:8765
                                  ▲
                                  └── 绕开：AP 客户端隔离、802.1x 认证、mDNS 被禁、NAT 回环

理由：企业/酒店 Wi-Fi 常开「客户端隔离」，两个设备互相 ping 不通；手机热点把「同网段」变成用户自己能控制的一件事，**不需要 IT 配合**。代价是手机耗电增加（热点 + 采集），需要实测 ⚠。

### 4.4 配对流程（二维码）

    1. PC 起服务（端口 8765 起，被占顺延）→ 生成一次性 token（TTL 60s）+ 自签证书指纹
    2. PC 浮窗显示二维码：earshot-sales://pair?v=1&ip=192.168.43.10&port=8765&tok=xxxx&fp=sha256:...
    3. 手机扫码 → 解析 → 尝试 TLS 直连（校验指纹）→ 发 hello（设备型号、系统版本、音源能力）
    4. 两端同时显示 4 位校验码（防中间人/防连错设备）→ 用户确认
    5. 建立会话：PC 下发参数（采样率、帧长、码率、判停参数版本）→ 开始推流
    6. 心跳 1s；3s 无心跳 → 判「链路异常」→ 显示状态 + 自动重连；token 过期则要求重新扫码

失败分支：直连超时（3s）→ 提示「两台设备不在同一网络」→ 引导开热点 / 或用中继二维码（第二张二维码携带 relay 地址）。

### 4.5 协议草案（预留，不实现）

帧格式（二进制，小端）：

    0        1        2        3        4                               N
    ┌────────┬────────┬────────┬────────┬───────────────────────────────┐
    │ VER=1  │ TYPE   │ FLAGS  │ RESERV │ PAYLOAD                       │
    └────────┴────────┴────────┴────────┴───────────────────────────────┘

消息类型：

| TYPE | 方向 | 含义 | 关键字段 |
|---|---|---|---|
| 0x01 | C→S | hello（握手） | 设备型号、OS 版本、音源类型、能力位 |
| 0x02 | S→C | hello_ack（参数下发） | session、采样率、帧长、码率、判停版本 |
| 0x10 | C→S | audio（Opus 帧） | seq(uint32)、ts_ms(uint64)、payload |
| 0x11 | C→S | audio_gap（补传标记） | from_seq、to_seq、gap_ms |
| 0x20 | C→S | state（采集状态） | 音源、音量、电量、前台/后台、锁屏 |
| 0x21 | C→S | call_state（通话状态） | 通话中/免提/耳机/蓝牙、AudioFocus |
| 0x30 | S→C | ctrl（控制） | pause/resume、增益、请求重连 |
| 0x31 | S→C | ack（确认） | 已收 seq、建议码率 |
| 0x40 | 双向 | ping/pong | rtt_ms |
| 0x50 | C→S | bye | 原因 |

约束：audio 帧必须单调递增；PC 端 jitter buffer 按 seq 重排、按 ts 对齐时钟；丢包用 Opus in-band FEC 恢复，连续丢包 > 5 帧打 gap 标记，**gap 前后的上文不参与 LLM 上下文**（避免把两段不相干的话连起来答）。

### 4.6 降级链（从好到坏，自动 + 手动）

| 级别 | 形式 | 触发条件 | 体验 |
|---|---|---|---|
| L0 | 局域网 WS + Opus | 同网段、扫码成功 | 实时，P50 1.5s |
| L1 | 手机热点 + 局域网 WS | L0 失败（隔离/NAT） | 实时，同上 |
| L2 | 云中继 WS + E2E 加密 | 手机与 PC 不同网络（4G/异地） | 实时，+80~250ms |
| L3 | USB 网络共享 / 有线 | 现场演示、Wi-Fi 极差 | 实时，最稳 |
| L4 | 录音补传（非实时） | 全程断网 | 通话后 1~3 分钟出「整通纪要 + 关键异议 + 建议话术」，不实时 |
| L5 | 纯离线话术卡 | 无手机、无网络 | 只按键盘搜索本地话术库（保底可用） |

### 4.7 异常矩阵（必须逐条实现并测试）

| 异常 | 现象 | 设计对策 | 用户可见反馈 |
|---|---|---|---|
| 切后台 | Android 采集被挂起 / 时间戳断裂 | 麦克风类型前台服务 + 常驻通知 + 电池白名单引导；AudioRecord 持续持有 | 手机通知常驻「正在辅助通话」；PC 显示「手机端已切后台」 |
| 锁屏 | CPU 休眠 → 丢帧；Wi-Fi 休眠 → 断流 | PARTIAL_WAKE_LOCK + WifiLock；锁屏后实测各厂商策略 | PC 显示「锁屏中，链路仍在」或「链路中断 N 秒」 |
| 断网 | 数据发不出 | 手机环形缓存 10~30s；重连后补传并打 gap 标记 | PC 顶部黄条「音频中断，正在重连（第 N 次）」 |
| 来电/其他 App 抢麦 | 采集中断 | AudioFocus 监听 → 暂停推流 → 恢复后自动续 | 手机/PC 同步显示「通话被系统打断」 |
| 蓝牙耳机插拔/切换 | 音源路由变化，音量突变 | 监听路由变化，重新选择音源并重标增益 | 显示「音源已切换：蓝牙耳机」 |
| Wi-Fi 漫游 / AP 切换 | 抖动飙升、短时断流 | jitter buffer 自适应放大到 120ms；断流 > 2s 走重连 | 链路健康条变黄 |
| PC 休眠/合盖 | 采集与推理停止 | SetThreadExecutionState 阻止休眠；合盖告警 | 弹窗提示「请勿合盖」 |
| 时钟漂移 | 长通话中 PC 端累积偏差 | 以 seq + 本地到达时间为准重采样对齐；每 30s 校正 | 无感 |
| 重复连接/串流 | 两个手机推到一台 PC | 一次性 token + 设备指纹 + 单活跃会话；旧会话踢下线并提示 | 「另一台手机已接管」 |
| 手机过热/省电模式 | 编码丢帧、CPU 降频 | 降码率到 16kbps；关闭本地降噪；提示「省电模式可能影响采集」 | 链路健康条变黄 |
| iOS 静音开关 | 不影响录音（录音走录音通道） | 无需处理，但需实测 ⚠ | — |
| 用户手动关闭采集 | 合规要求必须可关 | 手机端一键停止 + PC 端同步显示 | 双方都明确「已停止采集」 |

## 5. 音频与合规边界

> 本节是全文档最需要「说清楚做不到什么」的部分。任何「我们能偷偷录」的说法都不能进产品需求。

### 5.1 平台能力现状（公开资料）

| 平台 | 能力 | 结论 | 依据 |
|---|---|---|---|
| Android 10+ | AudioPlaybackCapture（应用内录） | **抓不到通话音频**。该 API 只捕获允许捕获的媒体类音频；USAGE_VOICE_COMMUNICATION 明确不在捕获范围 | [公开资料] Android 官方 API 文档 + AOSP 提交说明「All other usages (eg. USAGE_VOICE_COMMUNICATION) will not be captured」 + StackOverflow 实测反馈 |
| Google Play | 通话录音类 App 上架 | **不可**。2022-05-11 起政策明确：Accessibility API 不得用于远程通话录音 | [公开资料] Google Play 敏感权限与 API 政策 + The Verge / Engadget 报道 |
| Android 14+ | 麦克风前台服务 | 可用，但**必须 while-in-use 启动**，且声明 FOREGROUND_SERVICE_MICROPHONE | [公开资料] Android 官方前台服务类型文档 |
| Android 各厂商 | 系统自带通话录音 | 部分国产 ROM 自带（是否提示对方因厂商而异）；**文件事后可得，无法实时取流** | [公开资料] 一般性事实，需按机型实测 |
| iOS（全版本） | 第三方录制蜂窝通话 | **不可**。Apple 官方论坛：「There's no supported API to record voice calls managed by other apps (including the built-in Phone app).」；2025 年官方回帖仍称「We don't currently have any API that would allow an app to capture the audio content of a cellular call.」 | [公开资料] Apple Developer Forums |
| iOS 18+ | 系统「通话录音」功能 | 系统能力，部分地区可用，录音会**播报提示**；**第三方无法实时读取该录音流** | [公开资料] 需按地区实测 |
| 通用 | 蓝牙 HFP/SCO | 通话音频走 SCO 链路并被通话应用独占，第三方 App 取不到 | [公开资料] 一般性事实，需实测 |

### 5.2 五条采集路径的能力矩阵

| 编号 | 路径 | 实时性 | 音频质量 | 说话人分离 | 权限/政策 | 法律风险 | 结论 |
|---|---|---|---|---|---|---|---|
| **A** | 企业 CTI / SIP / 云呼叫中心双声道 RTP 旁路 | 实时（最优） | 最好（窄带/宽带清晰） | **天然分离**（左坐席右客户） | 需客户方 IT 配合；坐席侧统一录音告知是行业常态 | 最低（企业合规流程内） | **To B 终局** |
| **B1** | 通话耳机输出**模拟分线**（USB-C/3.5mm 分线器 + 第二设备/声卡 line-in） | 实时 | 好（只取下行=客户） | **天然只有客户** | 无需录音 App 权限；纯硬件 | 中（仍需告知） | **To C 首选（MVP）** |
| **B2** | 手机免提外放 + 第二设备近场拾音 | 实时 | 中（环境噪声、混入销售声音） | 混轨，需近似分离 | 无 | 中 | 降级方案 |
| **C** | 手机 App 直接录麦克风（免提场景） | 实时 | 中 | 混轨 | Android 14+ 前台服务要求；Play 不可上架（若用于通话录音）；iOS 不可用 | 中 | **仅内部灰度/特定机型，不作为承诺** |
| **D** | 系统自带通话录音文件 | 非实时（事后） | 好 | 因厂商而异 | 依赖 ROM | 中 | 只能做「通话后复盘」，不做实时 |
| **E** | iOS 第三方录通话 | — | — | — | **不可行** | — | **明确不做** |

**推荐组合**：
- To B：A（主）+ B2（客户没有话务系统时的过渡）。
- To C：B1（主）+ D（事后复盘）+ C（仅在其机型实测通过时灰度）。

### 5.3 法律与合规（中国境内为主，境外需当地法务）

| 事项 | 要求 | 设计上怎么落实 |
|---|---|---|
| 民法典第 1033 条 | 除法律另有规定或权利人明确同意外，不得「拍摄、窥视、**窃听**、公开他人的私密活动」 | 通话内容属私密活动：**必须取得客户明确同意**，且可撤回 |
| 个人信息保护法 | 告知—同意、最小必要、单独同意（敏感个人信息，如声纹）、可删除、可查阅 | 采集前告知页 + 同意记录（时间戳/话术版本/操作人）；声纹功能默认关闭 |
| 数据安全法 / 网络安全法 | 数据分级、留存期限、境内存储 | 客户通话数据默认**不出境、不出局域网**；云中继只转发密文 |
| 民事证据规则 | 以严重侵害他人合法权益方式取得的证据可能被排除 | 与「明确同意」绑定：有同意的录音可用于质检/复盘 |
| 美国各州 | one-party / two-party consent 差异（如加州等需双方同意） | 默认按**最严格**（双方同意）设计，不提供「单方同意」开关 |
| 欧盟 GDPR | 合法基础 + 告知 + 存储限制 + 数据主体权利 | 同上；不允许的市场不做 |

### 5.4 产品必须内置的合规机制（硬门禁，不可配置绕过）

1. **采集前告知**：通话开始 3 秒内，手机端播报/显示标准告知话术（可自定义、可多语言），PC 端同步显示告知状态。
2. **同意门禁**：客户口头确认（或坐席按合规话术确认）后，**才允许开始推流**；未确认 → 采集端本地不编码、不上行（不是「只是不显示」）。
3. **同意记录**：记录「告知时间、话术版本、确认方式、操作人、通话标识」，进入审计日志（不含通话内容）。
4. **随时中断**：手机端一键停止 + PC 端 Ctrl+Shift+H 隐藏 + 一键清除本场数据。
5. **客户可查可删**：提供按通话标识删除的接口（企业版必须，个人版做「本场立即删除」）。
6. **不做隐蔽**：不提供「隐藏通知/伪装图标/绕过系统录音提示」的任何功能；不针对检测做对抗。
7. **不做违反商店政策的分发**：不上架 Google Play 做通话录音；个人版走侧载/企业 MDM，并在安装页明确告知用途与法律要求。

### 5.5 加密、本地优先与留存策略

| 数据 | 默认 | 可选 | 加密 | 留存 |
|---|---|---|---|---|
| 原始音频 | **不落盘**（流式） | 本地调试留 20 段（沿用面试版 .tmp 策略，约 180KB/段） | 若留存：AES-256-GCM，密钥由 Windows DPAPI / Android Keystore 托管 | 默认 0 天；调试 20 段自动清理 |
| 转写文本 | 内存 + 会话结束即弃 | 存本地 JSONL 用于复盘 | 同上 | 默认 7 天可配；含 PII 的字段单独标记 |
| 卡片与采纳记录 | 只存卡片 ID + 来源 + 时间 | 存全文 | 同上 | 90 天（用于效果分析，不含客户原文） |
| 审计日志 | 存（不含通话内容） | — | 本地 | 180 天 |
| 上云内容 | 仅「客户当前这句 + 检索片段」，且过 PII 脱敏与红线守卫 | — | TLS | 按 LLM 供应商条款，需在合同中固定「不用于训练」 |

### 5.6 能做 / 不能承诺 / 不做

**能做（可写进 PRD）**
- 在客户**明确同意**的前提下，实时转写客户侧语音并给出提示。
- 企业话务系统（CTI/SIP/云呼叫中心）双声道接入，说话人天然分离。
- 模拟分线拾取通话下行（客户侧）音频（需配套硬件配件，需按机型验证）。
- 局域网内音频不上互联网（TLS + 指纹固定）；断网可离线用本地话术库。
- 默认不做声纹、不做人脸、不做情绪识别。

**不能承诺（写进合同也不会兑现）**
- 「任何 Android 手机都能后台录通话」。
- 「iOS 能录通话」。
- 「客户不会发现」——不提供隐蔽模式，也不保证。
- 「所有机型都能稳定 2 小时不中断」——机型/厂商差异大，需逐机型验证清单。
- 「自动替销售说话/自动发消息给客户」——MVP 不做，且合规上不建议。
- 「法律合规由本产品保证」——产品提供机制，合规责任在使用的企业/个人。

**不做（明确拒绝）**
- 隐蔽录音、伪装图标、绕过系统录音提示。
- 越狱/Root 方案、注入通话进程。
- 对抗会议/通话软件的检测与取证。
- 用 LLM 生成价格、折扣、合同条款、承诺函。
- 未经同意的「沉默采集」（哪怕技术上可行）。

## 6. 销售对客逻辑设计

### 6.1 目标与三条原则

**目标**：在客户说完话之后，让销售在 1~2 秒内看到「下一步做什么」，且**不打断对话**。

- **原则 1：只提示，不代答。** 所有输出是「可选动作」，不是「必须念的稿」。
- **原则 2：宁可不出卡，也不出错卡。** 置信度不够 → 进候选抽屉，不上主屏。
- **原则 3：数字与承诺必须来自结构化数据。** LLM 只做措辞，不做事实。

### 6.2 语料库结构

    销售语料根目录（沿用现有 knowledge/ 的「资料包」机制，按产品线/行业分包）
    ├── _base/
    │   ├── 公司介绍与资质.md

    │       ├── 适用场景.md

### 6.3 检索：双通道 + 卡片路由

    客户话语（ASR 后）
        │
        ├─[通道 1] 结构化精确匹配（0 LLM，最高优先级）
        │     型号/产品名 → 功能清单、价格表、条款
        │     竞品名 → 竞品对比卡
        │     价格/折扣关键词 → 价格卡（模板填充）
        │     命中即出卡，不再走 LLM
        │
        └─[通道 2] BM25 语义召回（复用 knowledge.py）
              异议库 / 案例库 / playbook → top-2 片段
                    └─► 有结构化骨架 → 模板卡 + LLM 润色一句话
                    └─► 无骨架 → LLM 生成（必须带 sources，且过红线守卫）

融合规则：结构化命中优先（专业场景下「精确」比「相似」重要）；两路都空 → 不出卡（不要用 LLM 硬编）。RRF 只在同一路内部做融合——面试版已实测异构通道融合会互相拖累，字级 bigram 通道负收益且默认关闭，销售版继续默认关闭 bigram。

| 需求挖掘 | 客户描述现状/痛点/目标 | 出现明确需求确认或客户反问 | 挖掘问题库、行业案例 | 不要报价 |
| 方案呈现 | 客户问「你们怎么做/有什么功能」 | 客户提异议或问价 | 功能卡、场景卡、案例卡 | 不要贬低竞品 |
| 异议处理 | 异议词（贵/再看看/已有供应商/不需要/没预算/决策人不是我） | 客户认可或转向新需求 | 异议应答卡（三层）、证据卡 | 不要硬顶、不要承诺 |
| 逼单 | 客户问折扣/合同/上线时间/试用；或销售主动推进 | 客户同意下一步 or 拒绝 | 推进卡（约演示/试用/方案会）、价格卡 | 不要越权折扣 |
| 收尾 | 约定下一步 / 客户说忙 | 通话结束 | 纪要点、下一步确认卡、资料卡 | 不要拖 |
| 异常态 | 客户明确拒绝/情绪负面/要求停止录音 | 客户改口 or 结束 | 体面结束卡、转人工卡 | 不要继续推 |

实现要点：
- **滞回**：状态切换需要连续 2 个信号或 1 个强信号，避免一句「贵」就跳到异议态。
- **手动覆盖**：销售可用快捷键锁定阶段（1~6 键），状态机不再自动跳（人会比模型准）。
- **状态日志**：记录「何时进入何状态、依据哪句话」，用于复盘与标注。
- **未验证**：状态机准确率需用真实销售通话标注验证（见 7.3）。面试版的 100% 路由准确率是**同一场数据拟合上限**，不能外推。

### 6.5 话语行为分类器（复用 router.py 改造）

| 类别 | 典型说法 | 触发 | 出卡 |
|---|---|---|---|
| ask_feature 问功能 | 「你们能对接 ERP 吗」 | 功能清单命中 | 功能卡（status=released/beta 精确） |
| ask_price 问价 | 「大概什么价位」 | 价格词 + 价格表 | 价格卡（模板） |
| objection 异议 | 「太贵了 / 再考虑考虑 / 已经有供应商了」 | 异议词表 + 语义 | 异议卡（三层） |
| competitor 竞品 | 「我们在看 X 家」 | 竞品名表 | 对比卡（不贬低） |
| buying_signal 成交信号 | 「怎么签 / 能试用吗 / 什么时候能上」 | 信号词表 | 推进卡 |

| unclear | 噪声/听不清 | 低置信 | 不出卡 |

### 6.6 提示优先级与「不抢话」策略

**优先级公式（用于同屏排序，硬规则优先于公式）**

    Priority = 100×合规旗标 + 60×成交/风险信号 + 40×阶段匹配 + 30×新鲜度 + 20×置信度 − 50×打断成本

**硬规则（比公式优先，任何情况不可违背）**

1. **客户正在说话 → 不出新卡。** 判断依据：客户侧 VAD 处于「说话中」。此时只做「预计算」，把卡片放进队列。
2. **销售自己正在说话 → 不出新卡。** 判断依据：PC 麦克风能量（只算能量、不转写）。避免销售一边说一边被屏幕带偏。
3. **判停后 0~300ms 内一次性推 1 主卡 + 最多 2 副卡**，不流式刷屏。
4. **同屏最多 1 主 + 2 副 + 1 合规警告**；一张主卡最多 2 行、每行 ≤ 28 字（销售没时间读）。
5. **主题冷却**：同一 objection_type / 同一产品 30s 内不重复推。
6. **频率上限**：每 10s 最多 2 张新卡；每通电话最多 40 张卡（超过说明检索没用）。
7. **过期即消失**：卡片带 TTL（价格卡 30s、异议卡 30s、推进卡 20s），过期降级进抽屉，不留在屏幕上误导。
8. **客户沉默 > 8s** → 推「下一个问题」卡（主动推进等，属于销售场景的高价值时机）。
9. **合规风险命中（客户提到录音/隐私/骚扰）** → 立即停止采集 + 全屏提示 + 记录审计，优先级最高。

**「预出卡」补偿判停延迟**：客户还在说话时，PC 已用「半句」跑检索、把候选卡算好放在内存里；判停一发生只需 3ms 就上屏。这样既不用把 VAD 调到 400ms（会切碎句子），又能把「感知延迟」压到接近 LLM 首字。

### 6.7 话术置信度与人工确认

**置信度来源（禁止用 LLM 自评分——面试版已实测「检索分数当置信度」不成立）**

| 来源 | 权重 | 说明 |
|---|---|---|
| 结构化精确匹配（型号/价格/竞品名完全命中） | 高（0.9+） | 最可靠 |
| 规则词表强命中（异议词、成交信号词） | 中高（0.7~0.9） | 可解释 |
| BM25 检索分 + top-1 与 top-2 的差距 | 中（0.5~0.8） | 面试版实测分数只是排名函数，只能做相对比较 |
| 状态匹配度（当前阶段是否允许该卡） | 中 | 门控而非打分 |
| LLM 吐出的 sources 是否覆盖关键实体 | 中 | 只做否决项 |

**三档门控**

| 档位 | 条件 | 展示位置 |
|---|---|---|
| 主卡 | 置信度 ≥ 0.75 且过红线且阶段匹配 | 屏幕中央大字区 |
| 副卡 | 0.5~0.75 | 右侧队列（可点开） |
| 抽屉 | < 0.5 或阶段不匹配 | 快捷键 Tab 打开候选池（默认不展示） |

**人工确认**
- 卡片必须「点一下采纳」才计入采纳率；不点默认忽略（不自动执行任何动作）。
- 用户可对卡片「纠错」（错在哪：不该出现/内容错/时机错），用于优化规则，而不是训练模型。
- **绝不自动播报、绝不自动发消息、绝不自动写 CRM**（MVP 明确不做，Phase 2 再评估且需合规评审）。

### 6.8 价格 / 承诺 / 禁用话术：三条红线（硬拦截）

1. **价格红线**
   - 报价只能来自 price 表的 list_price 与 discount_policy；卡片显示「可自主折扣上限」。
   - 客户问到超出权限的折扣 → 卡片不出现任何数字，只出现「需申请，当前可承诺范围以价格表为准」。
   - 生成卡（LLM）里若出现价格数字 → 直接丢弃该卡，改用模板卡；这是**拦截**不是提示。
2. **承诺红线**
   - 功能卡必须显示 status（已发布 / beta / 规划中 / 不支持）；status=not_supported 或 planned 时，LLM 提示词里明确禁止说「我们有/可以做」。
   - 涉及合规、数据安全、SLA 的承诺，卡片只给「以正式合同/方案书为准」，不给具体承诺语。
3. **禁用话术红线**
   - 本地词表 + 正则：绝对化用语（「最好/第一/100%/保证」）、保收益（「保证回本/保证增长」）、贬低竞品（「他们不行/快倒闭了」）。
   - 命中 → 卡片顶部红条「这句话不能说」，并给替代表达。

### 6.9 敏感信息保护

- **PII 脱敏管道**（在拼接 LLM prompt 之前）：手机号、身份证、地址、银行卡、订单号、邮箱 → 占位符替换（如 CUST_PHONE）。回填只在本地屏幕显示时做。
- **敏感分级**：L2 条目（价格表、未公开条款、客户名单）**永不进入 LLM prompt**，只走本地模板。
- **出网守卫**：prompt 组装完成后，扫描敏感词表 + 价格数字模式，不通过则降级为本地模板卡（宁可少给信息）。
- **日志最小化**：默认只记卡片 ID / kind / 来源文档 / 时间 / 是否采纳；不记客户原话。需要复盘时由用户显式开启「本场记录」（保存到本地加密文件）。
- **屏幕隐私**：客户可能看到 PC 屏幕 → 卡片默认不显示客户姓名/电话/内部折扣等级；一键隐藏（复用面试版 Ctrl+Shift+H）；共享屏幕给客户时（演示场景）自动进入「演示模式」只显示产品资料。
- **声纹**（若启用）：属敏感个人信息，需单独同意、本地存储、可删除；默认关闭。

### 6.10 PC 浮窗改造（销售版 UI 契约）

    顶部：通话计时 ｜ 状态机阶段 ｜ 链路健康 ｜ 采集开关（明显可见）
    中部：主卡（大字，≤2 行，含「动作」动词开头）  +  红条警告（如禁用话术）
    右侧：副卡队列（最多 2 张，缩略）
    底部：客户最近一句（灰字） ｜ 热键提示
    展开：完整话术、证据来源、下一问题清单
    隐藏：一键（客户靠近/共享屏幕）；「演示模式」只显示产品资料

与面试版 UI 的三个差异：
1. **不要「核心句大字照念」的强视觉**——销售版是提示，不是提词；大字区放「动作」（问什么/别说什么），不放长句。
2. **状态可见**：阶段与采集状态必须常显（合规要求 + 用户信任）。
3. **反面保护**：面试版怕面试官看到屏幕；销售版既怕**客户**看到，也可能主动共享屏幕给客户 → 需要「演示模式」与「自动隐藏」规则。

### 7.3 可验证指标（三层，全部要有测量方法）

**技术层**

| 指标 | 目标 | 测量方法 |
|---|---|---|
| 端到端延迟（客户说完 → 卡上屏） | P50 ≤ 1.5s，P90 ≤ 2.2s | 埋点时间戳：判停时刻 / 首次推卡时刻；用 TTS 合成 + 真机回放 |
| 结构化卡延迟 | P50 ≤ 1.0s | 同上，标记 card.kind=price/spec |
| 语音链路中断次数 | ≤ 1 次/小时 | 链路日志（reconnect 事件） |
| 断线恢复时间 | ≤ 10s | 注入断网 5s/10s/30s |
| 丢包 2%/5% 下可识别率 | ≥ 95% / ≥ 85% | 网络注入 + ASR 结果对比 |
| 手机耗电 | ≤ 8%/小时（采集+热点） | 电量计实测 ⚠ 目标待校准 |
| PC 内存/CPU | 内存 ≤ 800MB，CPU 峰值 ≤ 60% | 复用面试版 rss 监控 |
| 连续运行稳定性 | 2 小时 0 崩溃 0 漏采 | 长会话压测 |

**质量层**

| 指标 | 目标 | 测量方法 |
|---|---|---|
| ASR 字符错误率（销售域） | ≤ 10%（待实测基线） | 200 句人工标注转写 |
| 检索 hit@3（异议/价格/功能三类） | ≥ 85% / ≥ 90% / ≥ 90% | 200 条标注问句，复用 tools/regress 思路 |
| 状态机准确率 | ≥ 80% | 200 轮对话人工标注 |
| 误推率 | ≤ 3 张/小时 | 标注 + 用户「纠错」埋点 |
| 抢话次数（客户说话中弹主卡） | **0** | 硬规则测试 + 日志断言 |
| 价格/功能幻觉 | **0** | 构造 100 条越权/超范围问题，断言卡片不含数字或明确 not_supported |
| 卡片相关性（人工 1~5 分） | ≥ 4.0 | 双人盲评 100 张 |

**业务层**

| 指标 | 目标 | 说明 |
|---|---|---|
| 采纳率 | ≥ 40%（试点期） | 点了「采纳」的卡 / 出的卡 |
| 销售主观评分 | ≥ 4/5 | 试点问卷 |
| 客户投诉 | 0 | 试点期 |
| 合规审计通过 | 100% | 每通有告知与同意记录 |
| 成单影响 | 不做承诺 | 需 A/B 且样本量足够，MVP 不设 KPI（否则会被当成「保证业绩」） |

> 诚实提醒：业务层指标在试点期**只能定性**。把「提升成单率」写进验收标准 = 给自己挖坑。

## 8. 诚实边界

### 8.1 需要用户/法务确认的假设（不确认就无法定稿）

| # | 假设 | 影响 |
|---|---|---|
| A1 | 目标客户是**个人销售**还是**企业销售团队** | 决定走路径 B（To C）还是 A（To B）；两者架构差异大 |
| A2 | 通话形态：蜂窝电话 / 企业 VoIP（企微、钉钉、飞书、腾讯会议）/ 呼叫中心 / 固话 | 决定采集方式与说话人分离方案 |
| A3 | 是否接受「双方告知」（客户会被明确告知） | 若不接受，本产品**不做**（无法律空间） |
| A4 | 是否有企业已有的录音/质检/CRM 系统可对接 | 决定 M5 走哪条企业通道 |
| A5 | 客户数据是否允许出局域网（LLM 调用） | 不允许则必须本机小模型，延迟与质量都会变 |
| A6 | 手机机型范围与分发方式（侧载/MDM/商店） | 决定能否做 App；iOS 若必须则功能受限 |
| A7 | 语料的来源、更新责任人与保密等级 | 决定语料 schema 与导入流程 |
| A8 | 预算/硬件（是否有 GPU 跑本地模型） | 决定「全本地」可行性 |
| A9 | 是否需要多语言/多地区（价格与合规随地区变） | 决定语料与合规分支复杂度 |
| A10 | 是否需要与 CRM 双向同步 | MVP 不做，但接口要预留 |

### 8.2 依赖未验证的手机能力（必须在 M0 实测，不得提前承诺）

| # | 能力 | 为什么不确定 |
|---|---|---|
| U1 | Android 免提通话中，第三方 App 能否稳定读到麦克风（且不被系统压成静音） | 各厂商 ROM/音频 HAL 差异大；通话音量路由不同 |
| U2 | 模拟分线在目标机型上是否可行（USB-C 音频路由、通话是否走该通路） | 依赖适配器与机型；部分机型强制扬声器 |
| U3 | iOS 后台持续录音的存活时长与审核风险 | 后台音频模式可声明，但商店审核与系统挂起策略需实测 |
| U4 | 锁屏后 Wi-Fi 与 CPU 是否持续 | 厂商省电策略差异极大（尤其国产 ROM） |
| U5 | AudioPlaybackCapture 对具体 VoIP 应用（企微/钉钉）是否可捕获 | 取决于对方 App 的 audio attributes 与 capture policy |
| U6 | 系统自带通话录音文件能否被第三方读取/导出 | 各 ROM 路径与权限不同 |
| U7 | 双设备时钟同步精度是否够做 20ms 级对齐 | 需要实测漂移 |
| U8 | BLE / LE Audio 在目标机型上的可用带宽与延迟 | 机型差异大，且不主流 |
| U9 | 手机端 Opus 编码在低端机上的实际耗时与耗电 | 未测 |
| U10 | 客户语音的远场 SNR（路径 B2 免提外放场景）是否够 ASR | 房间声学影响大 |

### 8.3 本文中「只是估算、未实测」的数字（不能当验收线）

- 手机链路各段：麦克风缓冲 40ms、编码 2ms、局域网 5ms、jitter 60ms、解码 2ms（全部 ⚠）
- 4G/5G + 云中继增量 80~250ms（⚠，强依赖地域与运营商）
- 销售语料检索 1~3ms（面试版 338 块是 0~1ms，销售语料规模未定）
- 手机耗电 8%/小时、带宽 10.8MB/小时（⚠ 由 24kbps 推算）
- 总工期 13~20 周（⚠ 不含法务与试点用户招募）
- 所有质量目标（hit@3 85%、状态机 80%、误推 ≤3/小时）都是**目标值**，需 M2/M3 用真实脱敏数据校准

### 8.4 继承自面试版的已知问题及在销售场景的影响

| 面试版已知问题 | 销售版是否更严重 | 处理 |
|---|---|---|
| 多人混轨分不清谁在说（面试版未解决） | **更严重**（销售对话必然双人） | 列为必解项：CTI 双声道优先，单声道用近似分离 + 输出「低置信」 |
| ASR 专名写坏 | **更严重**（型号/价格错一个字符 = 报错价） | termfix + 结构化精确匹配 + 卡片显示「以价格表为准」 |
| 话题续接失败（指代型追问） | 类似 | 状态机 + 对话历史；不追求 100% |
| 路由 100% 是拟合上限 | 相同 | 必须建销售域标注集，不接受「沿用面试版数字」 |
| 长会话 >1 小时稳定性未测 | 相同 | M1 起专项压测 |
| 能量 VAD 未与 Silero 对比 | 相同 | 销售场景噪声更复杂（车内/办公室），M1 补对比实测 |
| 防共享只挡截屏不挡拍屏 | **反向**（销售版会主动共享屏幕给客户） | 新增「演示模式」，不做安全承诺 |

### 8.5 不能承诺清单（再强调一次）

- 不承诺任何机型的「后台静默通话录音」。
- 不承诺 iOS 端通话录音。
- 不承诺「客户不会发现」。
- 不承诺「自动提高成单率」。
- 不承诺「法律合规由产品保证」。
- 不承诺「零延迟 / 客户还没说完就提示」（那会抢话）。

## 附录 B：复用与新建的边界（一句话版）
