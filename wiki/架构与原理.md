# EarShot（顺风耳）· 架构与原理

> 实时面试提词器，Windows 桌面浮窗。
> 一句话：**抓系统回环音频（只抓扬声器输出＝面试官）→ 本地离线识别 → VAD 判停 → 本地 BM25 检索自己的面试材料 → DeepSeek 流式生成"可照念"的口语答案 → PyQt6 浮窗上屏**。

本文说明"它由哪些部件构成、每个部件为什么这么做"。所有性能数字见 `docs/性能实测.md`，本文只引用结论、不复述表格。

---

## 一、总体架构

```
┌────────────────────────────── 本机（音频 / 识别 / 检索全离线）──────────────────────────────┐
│                                                                                          │
│  会议软件（腾讯会议 / 飞书 / 牛客 / 浏览器）                                                │
│      │ 声音从默认播放设备输出（耳机或扬声器都行）                                            │
│      ▼                                                                                   │
│  ┌────────────────────────────┐                                                          │
│  │ Windows 音频引擎（WASAPI）  │──回环（渲染流；麦克风那条线完全不碰）──┐                    │
│  └────────────────────────────┘                                     │                    │
│                                                                     ▼                    │
│  server/main.py（FastAPI + WebSocket，127.0.0.1，端口 8765 起，被占自动顺延）               │
│  ┌──────────────────────────────────────────────────────────────────────────────────────┐ │
│  │ asr_engine.py                                                                        │ │
│  │   LoopbackCapture（16 kHz / 单声道 / 20 ms 一帧）                                     │ │
│  │        ↓                                                                             │ │
│  │   EnergyVAD（600 ms 静音判停；20 s 上限在最安静处切）                                  │ │
│  │        ↓ 一段音频                                                                     │ │
│  │   SenseVoiceASR（ONNX int8，启动预热；每段落 .tmp/live_*.wav）                        │ │
│  │        ↓ 文本                                                                         │ │
│  │ extract_q.py（长段里只留"真在问我的那一句"）                                           │ │
│  │        ↓                                                                             │ │
│  │ router.py（提问判定 / 题型分类；skip 直接丢弃，不调模型）                              │ │
│  │        ↓ 提问                                                                         │ │
│  │ answer.py                                                                            │ │
│  │   ├ retrieve()        knowledge.py BM25（+ bank.py 题库）→ top-3 材料片段              │ │
│  │   ├ build_messages()  策略提示词 + 材料 + 公司背景 + 上文 + 名词告警                   │ │
│  │   ├ answer_stream()   → DeepSeek API（流式，thinking disabled）                       │ │
│  │   │                      失败/超时 → bank 离线题库兜底                                │ │
│  │   ├ check_answer()    答案后校验（数字出处 / 经历是否安在没准备过的词上）               │ │
│  │   └ bank.followups()  追问预案（本地算，0 延迟、0 成本）                               │ │
│  │ deep.py（可选）—— dsh --profile headless 子进程（手动触发，深度补充）                  │ │
│  └──────────────────────────────────┬───────────────────────────────────────────────────┘ │
│                                     │ WebSocket  ws://127.0.0.1:<port>/ws                 │
│                                     │ 每个事件带 qid，UI 只认当前题                        │
│                                     ▼                                                     │
│  ui/app.py（PyQt6 浮窗）                                                                   │
│  ┌──────────────────────────────────────────────────────────────────────────────────────┐ │
│  │ 置顶：WindowStaysOnTopHint｜Tool + 每 2 s SetWindowPos(HWND_TOPMOST) 保活              │ │
│  │ 防共享：SetWindowDisplayAffinity(hwnd, WDA_EXCLUDEFROMCAPTURE)                        │ │
│  │ 全局热键：RegisterHotKey（不依赖焦点；首选键被占自动换键并显示实际键位）                │ │

└──────────────────────────────────────────────────────────────────────────────────────────┘
```

**一句话读法：** 左边是"听见"（全离线），中间是"想"（本地检索 + 云端一次流式调用），右边是"看见"（浮窗）。三条边界清楚的职责，任何一条挂了都不该拖死另外两条。

## 二、模块职责与对应文件

| 文件 | 职责 | 关键实现点 |
|---|---|---|
| `server/main.py` | 进程编排：端口抢占、模型加载与预热、采集线程、事件广播、会话落盘 | 单实例守卫（端口真正 bind + 进程扫描）；`/healthz` 暴露 `ready`；WS 命令 `pause/resume/ask/deep` |
| `server/asr_engine.py` | 回环采集、VAD 端点检测、ASR 封装 | `LoopbackCapture` / `calibrate_threshold` / `EnergyVAD` / `SenseVoiceASR`（含 `warmup()`） |
| `server/extract_q.py` | 从面试官一整段转写里抽出"真正在问我的那一句" | 纯规则（标点 + 疑问词 + 长度 + 位置），抽不出就原样返回，绝不返回空串 |
| `server/router.py` | 提问判定 + 题型分类（决定用哪套回答策略） | 规则法；`skip`（设备调试 / 寒暄 / 自述）不发起模型调用 |
| `server/knowledge.py` | 语料切块、分词、BM25 索引与检索 | jieba + 领域词典；停用词过滤；文件名加权；强话题词加权；字级 bigram 通道（默认关） |
| `server/bank.py` | 会前题库：口语问法 → 可照念答案 | 三处用途：补充材料、离线兜底、追问预案 |
| `server/answer.py` | 策略提示词、检索组装、流式调用、答案后校验、材料外名词判定 | `decide_qtype` / `retrieve` / `build_messages` / `answer_stream` / `check_answer` / `is_unknown_gap` |
| `server/deep.py` | 深答线：调用 `dsh --profile headless` 子进程 | 超时 90 s；输出绑 `qid` |
| `ui/app.py` | PyQt6 浮窗：置顶 / 防共享 / 全局热键 / 事件渲染 / 自检 | `--selftest` 用假数据跑真路径并截图 |
| `tools/` | 运维与验证脚本 | 模型下载、题库/词表构建、会前自检、回归门禁、会话复盘、回放评测 |
| `config/` | 三个会前手填文件 + 配置文件 | `company.md` / `known_terms.md` / `never_used.md` / `settings.json`（可选） |

### WebSocket 协议（后端 → UI）

| 事件 | 内容 | UI 行为 |
|---|---|---|
| `hello` | 端口、`ready`、当前 `qid` | 建立连接后同步状态 |
| `status` | `loading_model` / `warming_up` / `indexing` / `listening` / `paused` / `audio_lost` / `audio_reconnecting` / `vad_calibrated` | 状态点颜色 + 文案；`audio_lost` 红字提示 |
| `level` | 回环 RMS（10 次/秒） | 底部电平条——"到底有没有在听"的唯一直观证据 |
| `asr` / `question` | 转写文本、音频时长、ASR 耗时 | 灰字显示面试官的话；`question` 同时切换 `qid` |
| `filtered` | 被判为"非提问"的句子 | 显示"已过滤(非提问)"，便于当场发现误杀 |
| `answer_start` | 题型标签（gap 时变琥珀色） | 顶部标签 |
| `answer_delta` / `answer_done` | 流式增量；结束时给首字 / 总耗时 / 来源 | 打字机渲染；核心大字即时更新 |
| `answer_warn` | 数字无出处 / 经历对不上 | 红标"照念前先看一眼"（只提示，不拦截） |
| `slow` | 首字看门狗超时 | 提示"这题先自己讲，出字了会自动上屏" |
| `preplan` | 追问预案（本地题库算） | 贴在核心框下，折叠状态也可见 |
| `deep_start` / `deep_done` | 深答线进度与结果 | 自动展开深答区 |

UI → 后端：`pause` / `resume` / `ask`（手动提问）/ `deep`（手动深答）。

## 三、为什么只抓系统回环，不抓麦克风

回环设备抓的是**渲染流**——操作系统准备播放出去的东西。带来的三个后果都是白拿的：

1. **天然区分说话人。** 麦克风那条线完全不碰，自己的声音永远不会进转写，不需要声纹分离、不需要回声消除。这是整套方案里最省事、也最稳的一步。
2. **戴耳机照样能抓。** 回环在渲染流的末端，与"声音从哪里放出来"无关。实测默认设备是耳机（`耳机 (Realtek(R) Audio)`）时回环信号充足。
3. **不打扰会议软件。** 不申请麦克风权限、不抢占采集设备，会议软件那边看不到异常。

代价是：**只能听见"对方"**。如果面试官的声音是从你的手机免提里传进来的，回环抓不到。这是设计取舍，不是缺陷。

## 四、音频链路：三个坑与对策

原始方案里点名的三个坑，实现时都做了对应处理，也都留了"看得见"的出口：

| 坑 | 现象 | 对策（实现处） |
|---|---|---|
| 系统提示音也会被采进去 | 微信钉钉提示音、音乐、键盘音效都会被转写 | 能量 VAD + 最短语音 300 ms 过滤；UI 上给"已过滤(非提问)"，误杀真问题可当场发现（`router.is_skip` + `extract_q`） |
| 会议软件用独占模式会抓不到 | 回环流是空的，整场静默 | 启动时**按房间底噪自动标定 VAD 阈值**（钳在 0.004~0.02，而不是写死 0.006）；底部电平条实时显示 RMS，按了暂停/设备不对一眼可见 |
| 没有声音 = 静默失败 | 用户以为在跑，其实一句没收到 | 会前自检 `tools/preflight.py` 含"当前有声音在放"一项；运行中每 5 秒检测默认播放设备是否变化，变了就报错重连（见下） |

采集之外的补充设计：**设备自愈**。旧版采集线程抛一次异常就退出——面试中插一下耳机，后半场就是静音。现在采集循环外层重连，退避 1 s → 15 s，同时把 `audio_lost` / `audio_reconnecting` 明说给 UI。长句也不硬切：到 20 s 上限时在最近几秒里挑**最安静的 300 ms** 处切开，后半段留作下一句的开头，避免在句子中间拦腰截断导致后面抽不出问题。

## 五、VAD 判停 600 ms 的取舍

端到端延迟预算里最大的一块不是模型，是"什么时候算他说完了"。

| 判停时长 | 收益 | 代价 |
|---|---|---|
| 300 ms（激进模式） | 端到端再省约 0.3 s | 面试官中途换气、想词时的自然停顿会被当成句末 → 一句被切成两半，两次识别、两次调用，答案还各答一半 |
| **600 ms（默认）** | 换气停顿不误判；实测端到端 1.3~1.5 s，已达成 ≤2.0 s 目标 | 每句固定多等 0.6 s |
| 1000 ms 以上 | 更稳 | 相对 1.3 s 的总预算，等待感明显 |

选择 600 ms 的理由是**总预算够用**：ASR 100 ms + 检索 1 ms + 首字 600~800 ms ≈ 0.7~0.9 s，加上判停仍在 2 s 目标内。用不到 0.3 s 去换"句子被切碎"的风险，不划算。

起判条件是**连续 160 ms 超过阈值**（不是单帧），进一步抑制瞬时噪声触发。阈值不是常数，启动时先采集约 1.5 s 底噪，取 `min(0.02, max(0.004, rms*3 + 0.002))`——真实面试里出现过面试官说"稍等，我把声音放大"，写死阈值必然踩坑。

### 为什么是能量 VAD，而不是方案里的 Silero-VAD

原始设计建议用 Silero-VAD（ONNX，约 2 MB，CPU 单帧 < 1 ms）。实际实现用的是**纯能量 VAD**（`server/asr_engine.py` 的 `EnergyVAD`：逐帧 RMS 与自适应阈值比较 + 端点状态机），可以从代码和文档核对的原因是：

- **不引入第二个模型与第二次神经网络推理。** 每帧只是一次 320 个采样点的 RMS 计算；ASR 那一次推理已经是这个链路里唯一的模型开销（80~115 ms）。模型下载脚本 `tools/download_model.py` 也只下载 SenseVoice 一组文件，装完即可用。
- **这里的判据本来就只需要"语音 / 静音"两态。** 信号来源是会议软件的回环渲染流：近场、无风噪、无远场混响，也不需要区分人声与音乐——正是能量判据最可靠的场景。
- **工程补偿都做在了这一层**：阈值启动自适应（不写死）、连续 160 ms 才起判、最短语音 300 ms 过滤、20 s 上限在最安静的 300 ms 处切开、暂停时直接 `reset()`。故障注入实测：200 块音频切 4 段、样本数一个不丢。

⚠️ **诚实标注：能量 VAD 与 Silero-VAD 没有做过对比实测（待补）**——没有两者在同一批真实音频上的准确率 / 误切率数据。仓库里 `tools/e2e_smoke.py` 还留着一句"极简能量 VAD：够 P0 用，后续可换 silero"，说明这是"先把链路跑通"阶段的取舍；如果实机上遇到"音乐/提示音被当成人声"或"轻声被吞掉"，换 Silero-VAD 是第一个该试的改动点。

## 六、ASR 选型：为什么是本地 SenseVoiceSmall ONNX int8

原始方案里列了云端流式（阿里 paraformer / 讯飞 / 腾讯）与本地 SenseVoice 两条路，并建议"云端为主 + 本地兜底"。实际落地选择了**纯本地单模型**，理由是实测数据推翻了当初对本地速度的担忧：

- 单次识别（2.4~4.1 s 音频）实测 **80~115 ms**，方案预估 200~500 ms，快 3~5 倍；RTF 0.025~0.03，比实时快约 38 倍。
- 进程内存 **491 MB**，预估 800~1200 MB。
- 零成本、零网络依赖、零额外 Key（DeepSeek 没有语音识别 API，选云端意味着必须再申请一家）。

既然本地已经比"网络往返 + 云端排队"更快更稳，双通道的复杂度就没有必要。

**两个必须记住的实现约束：**

1. **模型路径必须是纯 ASCII。** 中文路径下 `os.path.exists` 返回 True，但 sentencepiece 的 C++ 层报 `NOT_FOUND: No such file or directory`——Python 侧和 C++ 侧对同一路径的判断不一致，排查时极具误导性。`server/settings.py` 的 `ensure_ascii()` 在启动时即校验并抛出带修复提示的错误。
2. **必须预热。** 首次识别含 numba JIT 编译，要 **21.7 秒**；预热后约 100 ms。`boot()` 里显式调用 `warmup()`，并在 `/healthz` 的 `ready` 置位前完成——启动器轮询到 `ready` 才拉起浮窗。

模型由 `tools/download_model.py` 从 ModelScope `iic/SenseVoiceSmall-onnx` 下载（约 230 MB，纯标准库实现）。注意该仓库缺 `chn_jpn_yue_eng_ko_spectok.bpe.model`（368 KB），需从 `iic/SenseVoiceSmall` 单独取。

## 七、提问判定与抽取：先把"噪音"去掉

面试官的转写往往长这样（真实一面的原话）：

> "我为什么这么问呢？就是前面因为你说到你用了部分的三维的这些数据。但我听下来可能更多的是只是做一个给人来看的，就会不会碰到楼。"

整段丢给分类器和检索全是噪音，所以中间加了两道纯规则、零延迟的关卡：

1. **`extract_q.extract()`——抽句。** 只按句子切（绝不在逗号处动刀，逗号两边的成分相互依赖）；锚点是第一句"像在提问"的话；锚点前的自述丢掉，但命中"如果/假如/比如说"这类前提词时向前回带一句（设计题的条件常写在铺垫里，丢了会让分类从"设计题"掉到"经历题"）；一个问句都没有就原样返回，不猜。实测：44 条真实提问提取后**变类 0 条**，总字数 −16.1%，耗时 0.007 ms/次。
2. **`router.classify()`——分类 + 过滤。** 先判"是不是在问我"：设备调试、寒暄、面试官自述一律 `skip`，**不发起模型调用**。真实一面 50 段面试官发言里有 6 段是这类内容，等于省掉 12% 的调用和屏幕垃圾。剩下的按"该用哪套策略"分类，而不是按语言学分类。

分类策略与输出结构：

| 类型 | 判定特征 | 输出结构 |
|---|---|---|
| `experience` 经历深挖 | "你在""为什么用""怎么做的"（**真提问的兜底线**） | 【思路】【展开】【数字】 |
| `design` 开放式设计 | "如果让你""你会怎么""结合我们" | 【思路】【拆解】【落点】 |
| `behavior` 行为 | 冲突 / 缺点 / 失败 | 压缩版 STAR |
| `motivation` 动机意向 | "为什么选我们""职业规划" | 结合公司背景 + 具体经历 |
| `reverse` 反问机会 | "你有什么想问的" | 给 2~3 个有水平的问题 |
| `gap` 没准备过的名词 | 名词判定命中（见第十节） | 【坦诚】【我的理解】【迁移与路径】【反问】 |
| `skip` 非提问 | 设备 / 寒暄 / 自述 | 只显示，不调模型 |

**为什么"经历深挖"是兜底线**：真实一面 44 条提问里 39 条是项目深挖。经历线对材料最敏感、最不容易编，所以"是真提问但没命中任何信号"时按它走最安全。（这条规则是照同一场数据调的，换一场必须重测——参见第十四节“诚实边界”。）

## 八、检索：BM25 + jieba + 领域词典 + 文件名加权

检索在本地做，不占网络延迟（单次 0~1 ms）。语料 = 自己工作区的面试材料，按 Markdown 标题切块（300~700 字）。

调优是照着"真实口语提问"一步步抠出来的，每一步都对应一个真实故障：

| 步骤 | 解决的真实问题 |
|---|---|
| ① 去停用词 | "这个系统是**自己**搭的**吗**"里一半是虚词，把通用 HR 稿顶到第一，真正讲这个项目的报告掉到第 6 |
| ② jieba 领域词典 | "工作流"被切成"工作/流"、"有向图工作流"被切成"有向图/工作/流"，术语对不上 |
| ③ 文件名进词袋并加权（×4） | "那个推荐系统"就是 `项目A_推荐系统.md`，但正文里没有这个完整串 |
| ④ 上文 2 句当查询词 | 追问几乎都是"那你这个…""它还有一个…"，单句检索经常找不到主语 |
| ⑤ 强话题词加权（×3） | 话题切换时上文窗口会把检索拖回旧项目（"就是做了微调是吗"曾被答成"不是微调"） |
| ⑥ 话题持久化（回看上文 8 句继承）+ HR 守卫 | 本句既无实词也无话题词的短追问（"还有哪些角色呢""你做的占比多少"）只靠本句必然跑偏；但 HR/履历类问题**不该**继承项目话题，否则反而掉分 |

**字级 bigram 通道为何负收益、且默认关闭。** 动机是担心"整句没有实词"的口语追问检索不到，做法是去掉空白标点后切相邻两字单独建一路 BM25，两路各排名后用 RRF 融合。实测结论（39 条有明确材料的真实提问）：任何权重都不如纯词级——

| bigram 权重 | hit@1 | hit@3 |
|---|---|---|
| 0.0（纯词级，基线） | 69.2% | 84.6% |
| 0.2 | 66.7% | 82.1% |
| 0.3 | 69.2% | 79.5% |
| 0.5 | 66.7% | 79.5% |
| 0.7 | 66.7% | 76.9% |
| 1.0 | 64.1% | 76.9% |

单路对比同样更差（词级 27/39 hit@1、33/39 hit@3；bigram 单路 24/39、27/39），且**两路 top3 取并集一条都没多救回来**。根因：剩下未命中的那几条是"话题续接"失败，正确材料由好几轮之前的话题决定，gold chunk 在词级排 rank 5/7/16/5/54/43、在 bigram 排 47/7/27/22/20/9，两路都够不到 top3——这不是字面匹配能救的问题。

因此代码保留该通道但 `RRF_W_BIGRAM = 0.0`（此时排序与纯词级逐条一致），只在词级通道候选数少于 2 时当兜底（`BIGRAM_FALLBACK*`）。数据与口径写在 `server/knowledge.py` 文件头，避免后来者重复试错。

**题库并集。** 会前题库把"开放检索"变成"闭集匹配"：索引建在**口语问法**上而不是知识点上（"那个推荐系统是你自己搭的吗"而不是"介绍一下推荐系统的召回方案"）。题库独立 hit@3 61.5%，与主检索**并集 94.9%**，补上的正是"整句没实词"的那几条。但题库也有"问法像、话题不同"的噪音，所以它只作**补充材料**和**离线兜底**，不单独决定答案——实测命中组与未命中组的分数分布重叠（未命中最高 8.11 > 命中最低 4.89），按阈值硬切会把大量不相关问题直接铺出去。

## 九、双车道：快答线与深答线

| | 快答线 | 深答线 |
|---|---|---|
| 实现 | DeepSeek `deepseek-flash` 流式 + 本地检索 | `dsh --profile headless` 子进程（带工具，能联网） |
| 耗时 | 首字 0.3~0.8 s，总 0.9~1.6 s | 冷启动地板 9~13 s，实测 31.6 s |
| 用途 | **照念**（默认路径） | 手动触发的"深度补充" |
| 输出 | 【思路/核心】+ 展开 + 数字 | 思路 / 拆解 / 落点 |

原始设计的自动化协同（快答上屏 300 ms 后自动丢给深答线、结果追加到"深度补充"区）在实机上被**降级**了：31.6 s 的到达时间在面试里用不上，没人会等。现在的分工是——

- **快答线**是唯一默认在跑的线，只做"立刻能念"这一件事。
- **深答线**保留为手动能力（`Ctrl+Shift+D`，本机该键被别的软件占用，程序自动换成 `Ctrl+Shift+J`），输出同样绑 `qid`，不会贴到别的题上；超时从 240 s 收到 90 s。
- 原本指望深答线承担的"下一句可能问什么"，改由 **`bank.followups()` 追问预案**本地计算：题库是按材料章节生成的，同一章节的问法天然就是面试官接下来可能的追问，0 延迟、0 成本。

## 十、答案可信度：三道防线

提词器的错误只有两种是致命的：**念出一个材料里没有的数字**，和**把"我用过"安在自己没做过的东西上**。

**第一道：提示词铁律 + 分题型策略。** 所有策略共享的铁律写死三条——重点是"思路"不是"做法"；事实和数字只能来自 `<材料>` 或 `<上文>`，两处都没有就写"无"；`【思路】`那一句本身就是结论，不许写成"我判断面试官想问的是…"（实测这类元描述改造前占 37%，照念很尴尬，改后 0%）。此外有两条按问题分量适配的补充：**短确认题**（"是今年毕业的是吗？"，≤30 字、带"吗/是吧"且不含"为什么/怎么/哪些"）压到 60 字内；**列举题**（"还有哪些业务""占比多少"）要求第一句先给清单。

**第二道：材料外名词（gap）判定。** 起因是两次真实的编造事故：问"你用过 eBPF 做可观测性吗"，材料里出现 0 次，模型答"我用它做过节点级观测，挂 kprobe 抓系统调用"；问 Temporal 工作流引擎，答"用过，但我的主力是 LangGraph"。答案听起来最专业，但追问两层就穿帮，性质从"不会"变成"不诚实"。判定规则两个方向都防误报：

- **英文侧**：问题里出现"语料查无此词"的英文专名，且这句在问"了不了解 / 用没用过"。过滤版本号、单字母、通用词。
- **白名单** `config/known_terms.md`：**我会但材料里没写**的词（不含这道闸，"你用过 ONNX 吗"会被判成没准备过——这是最难看的误报）。
- **ASR 变体归一**：识别会把字母拆开（实测识别结果是"你在 r a g 项目里为什么用双塔加粗排"），而转写稿里又是另一种坏法（`lara←LoRA`、`lmm←LLM`、`rug←RAG`）。`normalize_terms()` 把散开字母拼回去，`fuzzy_known()` 用编辑距离 + 首字母分桶捞回写坏的已知词，并把"他说的 X 应该是 Y"写进提示词。排序必须按（距离 > 人工词典优先 > 语料频次）——第一版没排序时"Loar"被捞成 `load`、"ONN"被捞成 `one`，比不提示更糟。
- **中文侧** `unknown_cjk`：三道闸，宁可漏报不可误报——语料查无此词；成分里至少有一个连 jieba 通用词典都不认识（湖仓一体→湖仓、存算分离→存算；而"知识图谱/强化学习"每个成分 jieba 都认识，**按设计不判**）；成分必须全是名词性，否则"双塔你""这块怎么"也会被拼成新名词。
- 命中的题走 `S_GAP`：坦诚承认 → 按原理推（明确是推导，不是经历）→ 说能迁移的经验 → **反问一句**。反问首选用来对齐术语（"你说的 eBPF 是指内核态那套，还是某个具体观测工具？"）——面试官的话也是转写来的，先对齐再答，比照着错词答安全。

**第三道：运行时的答案后校验 `check_answer()`。** 规则写进提示词 ≠ 模型一定遵守。流式结束后（几十微秒）比对答案里的数字是否出现在本题材料 / 上文 / 提问中（放行 90.30=90.3、90.3←90.35 这类口语写法，拦住 50000 说成 500 这种位数不对的），以及 gap 题里有没有"我用过 X"这类第一人称经历句。命中就在浮窗贴红标 **"⚠ 数字 xxx 不在本题材料里"**——**只提示、不拦截**，照念前自己看一眼。

另外两个配套：`config/never_used.md`（材料里写了但我其实没做过 → 命中即走坦诚，不管材料里写了多少）；`tools/build_terms.py` 生成 `config/terms_review.md` 候选清单（一次性摊开材料里出现的英文技术词、材料里没有的词、中文高频名词），会前两分钟人工归档到上面两个文件。

## 十一、健壮性设计（"面试当场会咬人"的那批）

| 问题 | 设计 | 说明 |
|---|---|---|
| **答案串题** | 每个事件带 `qid`；`stale(qid)` 判断 | 换题后旧流被 `should_stop` 切断，UI 丢弃过期事件。"念错题"比不显示更坏 |
| **快答线卡住** | 独占 `timeout=8s` + `max_retries=1` + **首字 5 秒看门狗** + 题库兜底 | SDK 默认 read timeout 是 600 秒，网络一抖屏幕就永远停在半句。看门狗阈值定在 5 s（3 s 会在好网络下误报） |
| **首题慢** | 启动预热：`answer.warmup()` 发一个 1-token 请求 | 冷启动的 DNS + TLS 握手全在第一题上（实测首题 4000 ms、第二题 951 ms）。预热后首题 1264 ms、第二题 460 ms。第一题往往是自我介绍，最不该慢 |
| **模型没加载完就开浮窗** | `/healthz` 暴露 `ready`；启动器轮询到才拉浮窗 | 旧版把"首页能打开"当成就绪，第一题是在预热期问的，墙钟从 1.3 s 涨到 3.8 s |
| **音频掉了整场静默** | 采集外层重连，退避 1→15 s；每 5 s 检测默认设备变化 | 状态栏红字"音频掉了，正在重连（第 N 次）" |
| **端口 8765 被占** | 真实 bind 抢端口，失败顺延 8766~8769；实际端口写 `.runtime_port`；UI 每次重连重读该文件 | 旧版写死 8765，冲突即静默退出、浮窗永远"未连接" |
| **两个后端同时跑** | 三重守卫：进程扫描（含"正在启动、还没监听"的）+ 端口应答探测 + 抢到更靠前端口者保留 | 两个后端会同时录同一路音频（一句话识别两遍、屏幕上两份答案）并互相覆盖端口文件。另外**不设 `SO_REUSEADDR`**——Windows 上设了之后两个进程能同时 bind 同一端口 |
| **线程异常无人知** | `crash()` 把异常与堆栈追加到 `logs/backend_error.log` | 线程里的异常不会打到控制台，面试后能查 |
| **复盘没有数据** | 每题写 `logs/session_*.jsonl`（问题 / 答案 / 首字 / 总耗时 / 来源 / 告警 / 是否被切掉） | `tools/session_report.py` 直接出"哪几题答砸了" |
| **录音不该一直躺在磁盘** | `.tmp/live_*.wav` 只保留最近 20 段 | 每段约 180 KB |
| **热键被别的软件占用** | 每个热键排一串候选，注册到哪个用哪个，并把**实际生效的键**显示在浮窗底部 | 本机 `Ctrl+Shift+D` 被占（`winerr=1409`），实际落到 `Ctrl+Shift+J`。以底部提示行为准，别背表 |

## 十二、浮窗（PyQt6）三项硬需求

**为什么是 PyQt6 而不是 Electron：** 本机 Electron 44 完全跑不起来——GPU 进程反复崩溃（`exit_code=-2147483645` = STATUS_BREAKPOINT），`--disable-gpu` / `--in-process-gpu` / 软件渲染都试过，窗口要么崩要么画不出像素。PyQt6 同进程渲染一次就通，而且能自我截图验证（内容保护下系统截屏看不见窗口，但 `widget.grab()` 可以）。

| 需求 | 实现 | 验证 |
|---|---|---|
| **置顶（压过全屏会议窗）** | `WindowStaysOnTopHint｜Tool` + 每 2 秒 `SetWindowPos(hwnd, HWND_TOPMOST, ..., SWP_NOMOVE｜SWP_NOSIZE｜SWP_NOACTIVATE)` 保活 | 全屏会议窗口之上可见 |
| **屏幕共享不可见** | `SetWindowDisplayAffinity(hwnd, WDA_EXCLUDEFROMCAPTURE = 0x11)`（Win10 2004+） | 系统截屏里窗口完全消失 |
| **全局热键不依赖焦点** | `RegisterHotKey` + `QAbstractNativeEventFilter` 捞 `WM_HOTKEY` | 浮窗没有焦点时热键照常生效 |

两个实现细节值得记住：

- **`WM_HOTKEY` 会被 Qt 投递两次**（实测两次的 `message.time` 完全相同）。不去重的话，按一下等于按两下，toggle 类热键"看起来没反应"。过滤器按 `(wParam, time, lParam)` 去重。
- **`RegisterHotKey` 注册的热键不走 Qt 按键事件**，只能在原生消息过滤器里处理。注册失败要用带 `last-error` 的 `WinDLL` 拿 `winerr` 才能给出原因。

渲染侧的取舍：**默认只显示核心句**（20 px 大字 + 状态栏），展开区与深答区折叠，`Ctrl+Shift+E` 才展开——真实面试里注视时间是秒级的，多显示一段就是负担。核心句超过 40 字时左侧画黄线 + 黄色角标 + 字号自适应缩小，一眼就知道"这行太长，别照念"。分段渲染用**通用解析**（第一个出现的 `【X】` 段即核心大字，其余进展开区），不硬编码段名，经历题（【思路】【展开】【数字】）和设计题（【思路】【拆解】【落点】）都能正确上屏；模型偶尔丢掉 `【】` 标记（gap 策略实测出现过一次）时退回"第一句当核心大字"，避免核心栏只停在省略号。

## 十四、隐私与诚实边界

**隐私（可核对的边界，不是承诺）：**

- 音频采集、语音识别、材料检索**全部在本机**，不出网。
- 唯一出网的是生成答案时发往 DeepSeek API 的 **"问题 + 检索到的材料片段"**——也就是说，材料内容（含公司名与业务信息）会离开本机。
- 识别产生的音频片段落盘在 `.tmp/live_*.wav`，只保留最近 20 段；会话记录落 `logs/session_*.jsonl`。
- `WDA_EXCLUDEFROMCAPTURE` 只对**截屏/录屏**有效，挡不住"共享整个桌面 / 采集卡 / 放大镜"，也挡不住对方要求开摄像头或现场追问细节。逃生手段始终是 `Ctrl+Shift+H`。
- 密钥是明文文件，工作区不要同步到公共网盘。

**诚实边界（原文档明确写下的"做不到"）：**

- **材料外名词走"坦诚"话术，不编造**；但判定靠"材料里查无此词 + 这句在问我了不了解"，它只知道材料里有没有，不知道"材料里写了但我其实没做过"。
- **ASR 会把专有名词写坏**，不同引擎坏法不同（本地 ASR 会吐散开字母，转写稿里是 `lara←LoRA` 这类替换），两种都得防；仍然无法做到"识别所有专名"，目标只是**永不自信地说错**。
- **字级 bigram 检索通道实测负收益**，默认关闭（见第八节）。
- **话题续接失败是主要未解问题**：整句没有实词、正确材料由好几轮之前的话题决定的追问，关键词通道救不回来，只能靠会前题库覆盖。
- **路由分类 100% 是照同一场真实面试数据调出来的拟合上限**，不是泛化期望；换一场面试必须重跑 `tools/regress.py`。
- **多人混轨**：转写里分不清面试官在问谁。
- 词表（`known_terms.md` / `never_used.md`）**靠人工维护**，工具只把候选摊开。
